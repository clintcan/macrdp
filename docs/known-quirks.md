# Known behavioural quirks

- **RDPDR surface is a real NFS mount (Phase 2), read-write, no root/kext/FUSE — `nfsserve` + the built-in `mount_nfs`.** `src/rdpdr/surface.rs`. On connect, **each** redirected filesystem device is exposed by its own **in-process NFSv3 server** (`nfsserve`) bound to `127.0.0.1:0` (ephemeral port); `RdpdrFs` implements `nfsserve::NFSFileSystem` by translating each NFS op into RDPDR over the `RdpdrHandle` — reads via `list_dir`/`read_file`, writes via `write_file` (`DeviceWrite`), `set_len`/`remove`/`rename` (`SetInformation` with FileEndOfFile/Disposition/Rename), and `create`/`mkdir` (`DeviceCreate` with FILE_CREATE/FILE_OPEN_IF) — with a `path↔fileid` cache (NFS addresses by opaque u64 fileid, RDPDR by Windows backslash path — `intern()` assigns a stable id per path and remembers size/kind so `getattr` needn't re-stat; `forget()` evicts on delete/rename). macOS's built-in client mounts it `-o nolocks,vers=3,tcp,rsize=262144,wsize=262144,readahead=4,port=<p>,mountport=<p>,actimeo=5 localhost:/ <mountpoint>` (the modest 256 KiB transfer unit + shallow readahead are deliberate — see the A/V-contention note below). The kernel VFS drives lazy lookups as the user browses, so **full subdirectory navigation works** (this replaces the Phase-1c temp-folder/`NSFilePresenter` mirror, which was top-level-only — subdir contents showed as empty folders). **No root needed** for a loopback NFS mount onto a user-created mountpoint (verified). **`/Volumes` is `root:wheel` (not world-writable) on a stock Mac, so the `/Volumes/<label>` attempt always falls back** to `$TMPDIR/macrdp-rdpdr-<pid>/<label>/` (= `/var/folders/...`, **not** `/tmp` — look there when debugging); the mount still appears in Finder. The `/Volumes` branch only succeeds if macrdp runs as root (e.g. a future privileged-port LaunchDaemon). Cleanup: `Surface::Drop` (connection teardown) aborts the NFS accept-loop task and, on a detached thread, `umount -f`s + removes the mountpoint (+ prunes the empty per-pid parent); **SIGKILL/signal-exit leaks one mount + `$TMPDIR` folder** (Drop skipped — `umount` it manually; the OS clears `$TMPDIR`). **Every** redirected filesystem device gets its own mount/server/`RdpdrFs` (`MacRdpdrHandler` keeps a `HashMap<device_id, Surface>` so a re-announce — or a drive added mid-session — doesn't double-mount; distinct mountpoints come from each device's label, with `prepare_mountpoint` appending a numeric suffix on a label collision). **File reads/writes reuse a kept-open handle** (`RdpdrHandle`'s LRU `HandleCache`, cap `MAX_OPEN_HANDLES`=16, keyed by `(device_id, path, Read|Write)`): `read_file`/`write_file` `acquire()` a cached open handle (opening on a miss) and do NOT close after each op, so a large sequential transfer is ~1 open + N reads/writes instead of N×(open+act+close). Handles close on LRU eviction, on a failed op (`invalidate`), and — crucially — before a `remove`/`rename` (`evict_path` awaits the close so a still-open handle can't defer the delete-on-close or block the rename). Measured: an 8 MiB read = 1 effective open + steady reuse, **except** macOS fires a concurrent readahead burst (~18 parallel RPCs) at file-open that all miss the cold cache at once → a one-time burst of opens, of which all-but-one close their duplicate via the insert-reconciliation (the cache keeps the first winner). That cold-open burst is bounded by readahead depth and amortizes to ~1 open for large files; no single-flight coordination (deemed not worth the async complexity). `set_len`/`remove`/`rename`/`create`/`mkdir`/`list_dir` still open→act→close per call (not cached — they're one-shot). On disconnect the cache is dropped and its open handles leak server-side (the client reaps them when the channel closes). `setattr` only honors a **size change** (truncate/extend via FileEndOfFileInformation); mode/uid/gid/atime/mtime are accepted as no-ops since the surface doesn't model them (the cache's times are a fixed server-start stamp). Verified on FreeRDP end-to-end: read path (`ls` + **subdir nav** + `cat` + byte-exact 200 KB multi-chunk read) **and write path** — create, write, append, truncate-rewrite, `mkdir` + nested write, `rename`, delete file, delete dir, and a **byte-exact 500 KB multi-chunk copy-in (sha256 matches source and read-back)** — plus clean unmount on disconnect; read path also verified on **mstsc**. **Two simultaneous redirected drives** verified on FreeRDP (each mounts as its own volume, serves only its own tree, writes land in the right source, both unmount on disconnect). **`--enable-drive-redirection`-gated.** **Open files with the full `FILE_GENERIC_READ` set, not bare `GENERIC_READ`** (`RdpdrHandle::file_read_access` = `FILE_READ_DATA | FILE_READ_ATTRIBUTES | FILE_READ_EA | READ_CONTROL | SYNCHRONIZE`, plus `FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE` options and broad `FILE_SHARE_READ|WRITE|DELETE`): real Windows honors the requested rights strictly, so a synchronous `IRP_MJ_READ` on a handle opened without `SYNCHRONIZE` is denied with `STATUS_ACCESS_DENIED` — the create succeeds, the read fails. FreeRDP-as-client was lenient and accepted bare `GENERIC_READ`, masking it (same FreeRDP-lenient / mstsc-strict pattern as the handshake-ordering quirk below). Same lesson: **verify RDPDR file ops on mstsc, not just FreeRDP** — the write path (`RdpdrHandle::file_write_access` adds `FILE_WRITE_DATA | FILE_APPEND_DATA | FILE_WRITE_ATTRIBUTES | FILE_WRITE_EA`, and delete/rename open with `DELETE | SYNCHRONIZE`) is verified on FreeRDP and on **mstsc** (create / edit-save / mkdir / rename / delete in a writable folder like `Users\<you>\Documents`). **A `STATUS_ACCESS_DENIED` from writing to a non-writable target — e.g. the `C:\` root or `$Recycle.Bin`, which an unelevated mstsc session can't write — is Windows enforcing its own ACL, not a macrdp bug; it now maps to `NFS3ERR_ACCES` so Finder reports "permission denied" (and `RdpdrHandle` errors carry the `NtStatus` via `RdpdrStatus` for that mapping — `OBJECT_NAME_COLLISION`→EXIST, `NO_SUCH_FILE`→NOENT, etc.). Write somewhere the redirected user actually owns.**
- **Redirected-drive I/O can make audio choppy and video stutter — RDPDR shares the one RDP connection + the server's single socket-writer and single-threaded client loop with EGFX video and RDPSND audio.** Reported 2026-06-18. In `vendor/ironrdp-server/src/server.rs::client_loop`, inbound PDU processing, `dispatch_display` (video), `dispatch_audio` (RDPSND), and `dispatch_events` (CLIPRDR **+ RDPDR**) are cooperative futures in **one `tokio::select!` on one thread**, all sharing **one `SharedWriter` mutex** (`writer.lock().await` per write) and one `Rc<Mutex<self>>`. So a large or bursty RDPDR data PDU monopolizes the writer; audio's lag model (divergence (2)/(3)) then sees the stall and **drops stale waves** (= the choppiness) while video frames back up. Worst for **copy-*to*-drive** (big downstream `DeviceWrite` PDUs, same direction as A/V) and large read bursts (deep readahead = many concurrent reads saturating the shared connection). **Mitigations (two, layered):** (1) **cap the NFS transfer unit + readahead** so RDPDR PDUs/bursts stay small enough to interleave with A/V — `run_mount` uses `rsize=wsize=262144` (256 KiB, was 1 MiB) and `readahead=4` (macOS default ~16 was the source of the ~18-wide read burst). Trades peak drive throughput (more round-trips, kept cheap by the handle cache) for A/V smoothness. (2) **dispatch-partition deprioritizes RDPDR behind EGFX** (vendor server divergence (4)): `dispatch_server_events` now orders each batch CLIPRDR → {EGFX + rest} → RDPDR, so a big `DeviceWrite` can't be written ahead of the video frames in the same batch (the fix specifically for **video stutter** on copy-to-drive — `ServerEvent::Egfx` and `ServerEvent::Rdpdr` share that one task, so without it RDPDR bulk starved EGFX exactly as CLIPRDR used to). Note this partition helps **video** (same task); **audio** rides its own `dispatch_audio` task and only benefits from mitigation (1) + the shared-writer being held for shorter chunks. Verified the smaller-unit mount still reads/writes byte-exact + navigates subdirs on FreeRDP (loopback can't reproduce the bandwidth contention itself — confirm smoothness on a real link). If it's still not smooth enough under heavy drive load, the deeper fix is architectural: replace the N racing dispatch futures with **one writer task that drains all channels audio-first** (can only reorder the single connection's writes, not parallelize them) — a larger vendored change, not done. (Aside: a flaky **CLIPRDR** "no reply in 10 s" → error 1359 teardown shows up with headless `sdl-freerdp`; it's a FreeRDP-test-harness artifact — disable client clipboard (`-clipboard`) when isolating RDPDR — not the same issue.)
- **RDPDR (drive redirection) init: mstsc requires the server to send Server Core Capability Request AND Server Client ID Confirm *before* it replies — FreeRDP is lenient and masks this.** Found 2026-06-16 building RDPDR Phase 1a. The MS-RDPEFS server-init order (3.3.5.1) is: Server Announce → [client: Announce Reply + Client Name] → **Server Core Capability Request → Server Client ID Confirm** → [client: Core Capability Response + Device List Announce]. The first cut sent only the Capability Request on Announce Reply and withheld the Client ID Confirm until *after* the client's Capability Response. **FreeRDP replied to just the Capability Request (lenient) so it worked; mstsc strictly waits for the Client ID Confirm and never sends its Capability Response → the handshake deadlocks after "Client Name" and no drive is ever announced.** The connection otherwise looks healthy (cliprdr/EGFX/audio all init), so the only symptom is "no RDPDR lines." Fix (`vendor/ironrdp-server/src/rdpdr.rs`): on Client Announce Reply, return **both** the Capability Request and the Client ID Confirm; send User Logged On on the Capability Response. Verified on mstsc (C: drive announced) and FreeRDP. Lesson reinforced: **verify RDPDR — and protocol handshakes generally — on mstsc, not just FreeRDP**; FreeRDP's leniency hides ordering bugs a real Windows client enforces. (Debugging note: the server's `start()`/handshake logs are at `debug` under `ironrdp_server::rdpdr`; the agent runs at `info`, and changing a LaunchAgent's `RUST_LOG` needs a full `bootout`+`bootstrap` — `kickstart -k` reuses the loaded job's env and silently keeps the old value.)
- **Password-manager windows and DRM video (Netflix etc.) show up blank/black — macOS excludes protected content from screen capture, and we can't (and shouldn't) override it.** Reported as a "why don't these appear?" question 2026-06-16. macrdp captures the whole display via ScreenCaptureKit and excludes nothing itself (`capture.rs` builds the filter with `with_excluding_windows(&[])`); the blanking is the OS protecting content, which SCK honors — so the protected window simply isn't in the pixels we get. Two distinct mechanisms, same visible result and same root cause ("the OS won't put this in a screen capture"):
  - **App-opted-out windows** — password managers (1Password et al.) set `NSWindow.sharingType = .none` on their vault / secret windows so screen-recording malware can't grab credentials. Such windows come through blank/black or absent. Per-window and display-independent (same on the primary panel or a virtual display).
  - **DRM-protected video** — Netflix / Apple TV+ / Disney+ / Amazon use FairPlay/Widevine hardware DRM; the compositor refuses to composite protected frames into *any* capture, so the video region is black while the page chrome, controls, and cursor render normally. **Audio still plays** (DRM blacks the picture, not the sound) — a useful tell that it's DRM, not a macrdp glitch. Non-DRM streaming (YouTube, Twitch, most HTML5 video) captures fine.

  **Not fixable from macrdp**, by design: ScreenCaptureKit has no "ignore sharing type / capture protected content" option, capturing protected content needs Apple entitlements an unsigned / Developer-ID app can't get, and overriding it would defeat the exact security guarantee these apps rely on (exfiltration over the network is their threat model). It's identical to what you'd see in QuickTime screen recording or a Zoom screen-share. **Do NOT chase a "fix"** — document it as a limitation. User workarounds: copy a credential to the clipboard and paste it across (the CLIPRDR channel syncs text fine); use a browser-extension autofill / menu-bar quick-access panel that may not be capture-excluded; for DRM video there is no workaround.
- **The audio SCStream must bind to the SAME display the video captures, or `--detach-primary` / `--capture-primary` kill audio.** Reported 2026-06-16 (mstsc): with `--virtual-display --detach-primary`, audio cut out on connect (and on reconnect played <1 s then died); with `--virtual-display --capture-primary` it stuttered in/out for a while. Root cause: `audio.rs::capture_loop` bound its `SCContentFilter` to `displays.first()` — the **physical primary** — even when video captured the **virtual** display. Both headless modes act on the physical panel once a client connects (`--detach-primary` disables it via `CGSConfigureDisplayEnabled`; `--capture-primary` `CGDisplayCapture`s + gamma-blacks it), which invalidates an SCStream whose content source is that panel: the audio stream ends (yields `None`), the self-heal restart loop rebuilds it against the same dead source, and you get silence (detach) or in/out thrash as each rebuilt stream briefly delivers then dies (capture). The video stream was immune because it already targets the virtual display, which survives both. Fix: thread the video path's `capture_display_id` into `MacRdpsnd` → `capture_loop` and select the matching display (`displays.iter().find(|d| d.display_id() == id)`, fall back to first), so the audio filter follows the virtual display. The filter is built once and reused across every restart-loop rebuild, so the source stays valid for the whole session. SCK system-audio capture (`captures_audio=true`) records all system output regardless of which display anchors the filter — the display is just the required content source — so binding to the virtual display loses no audio. A `bound_display_id` debug line (`RUST_LOG=macrdp::audio=debug`) shows which display audio attached to. Mirror-primary (no virtual display) was never affected (`target_display_id=None` → `first()`, unchanged).
- **Non-US keyboard layouts (`--keyboard-layout`) translate server-side via UCKeyTranslate and post Unicode — they do NOT switch the Mac's input source.** Built 2026-06-16. RDP clients send PS/2 *positional* scancodes, not characters; `input.rs` maps those to macOS virtual keycodes (also positional) and macOS turns a keycode into a character using **the Mac's active input source** — so a non-US client on a US-configured Mac types the wrong letters. The chosen fix (`src/keyboard_layout.rs`) resolves the requested layout to a macOS `UCKeyboardLayout` (via `TISCreateInputSourceList` on the input-source id, falling back to `TISCopyInputSourceForLanguage`) and, for each ordinary typing key, calls `UCKeyTranslate(keycode, modifier-state)` → Unicode, which `input.rs::key` posts as a string event (keycode 0 + `set_string_from_utf16`, the same mechanism as the RDP Unicode-keyboard path). **The alternative — `TISSelectInputSource` to switch the Mac's active layout — was explicitly rejected**: it would change the *local* Mac's keyboard while connected (visible/disruptive to a local user in mirror mode). Load-bearing details: (1) **Only the contiguous ANSI block is translated** — `is_translatable_keycode` = vk ≤ 0x32 **minus Return (0x24), Tab (0x30), Space (0x31)**; those three plus everything ≥0x33 (arrows, F-keys, keypad, editing) must stay on the keycode path so they behave as *keys*, not literal characters. (2) **Cmd/Ctrl combos are NOT translated** (gated on `!has_cmd() && !has_ctrl()`) so app shortcuts (Cmd+C, Cmd+Q) keep firing as keycodes; Shift/Option(AltGr)/Caps ARE folded into the translation (Option→AltGr chars like €). (3) **Dead keys compose** because `dead_key_state` persists across calls — a dead key returns `Some("")` (swallowed; nothing posted) and the accent lands on the next keystroke. (4) **The key-up is swallowed too** for translated keys — Unicode string events have no release side, so posting a bare key-up would desync the focused app. (5) The Unicode event is posted with **no modifier flags** (the shift/option were already baked into the character) so the app doesn't re-apply them. **Auto-detect is the default**: the KLID arrives in the GCC Client Core Data (`keyboard_layout: u32`, the same block the desktop-size feature reads), so the vendored acceptor captures it (acceptor divergence (2)) onto `AcceptorResult`, the vendored server publishes it to a shared `Arc<AtomicU32>` in `client_accepted` (server divergence (10)), and `input.rs` reads that cell to auto-select the matching layout on the first keystroke (re-checking on change, so a reconnect from a different client is handled) — **US English (0x0409) and unknown (0) keep the positional keycode path**, so the US majority is unaffected. `--keyboard-layout <spec>` overrides auto-detect (force a specific layout); `--keyboard-layout none`/`off` forces positional keycodes (disable translation entirely). Verified: US-layout translation unit-tested end-to-end (A→a, Shift→A, Caps→A, 1→1, Shift+1→!), and auto-detect verified live — sdl-freerdp `/kbd:layout:0x040C` made the server log `client keyboard layout announced klid=1036` and the input handler `auto-selected … layout=com.apple.keylayout.French`. The layout must be installed on the Mac (we pass `include_all=1` so even non-enabled bundled layouts resolve).
- **Ctrl→Cmd Windows-shortcut remap (`--map-ctrl-to-cmd`, opt-in) swaps the modifier per-key in `input.rs`; terminals are auto-suppressed, embedded terminals need `--no-remap-apps`.** Built 2026-06-21 on feedback from Devolutions' (IronRDP's) CTO daily-driving macrdp via mstsc: Windows muscle memory (`Ctrl+C/V/X/…`) doesn't trigger macOS copy/paste (which use Cmd), forcing the client's Win→Cmd key. With the flag on, `input.rs::key` rewrites a **curated vk set** — C V X A Z S F N T W O P R G (copy/paste/cut/select-all/undo/save/find/new/new-tab/close/open/print/reload/find-next) — from `Ctrl+<key>` to `Cmd+<key>` via `post_ctrl_as_cmd`: it clears Control (CGEventFlag + `NX_DEVICE_{L,R}_CTRL`) and sets Command (`NX_DEVICE_L_CMD`) in the swapped flags, posts a `FlagsChanged` carrying those on **both** event sources (so `[NSEvent modifierFlags]` reads Cmd), then the key-down; the matching key-up (tracked in a `remapped_keys: HashSet<u16>`, mirroring `consumed_keys`) posts with swapped flags then restores the real Ctrl state via `post_flags_changed`. Shift/Caps carry through, so `Ctrl+Shift+Z` → `Cmd+Shift+Z` (redo) works. **Load-bearing choices:** (1) **Off by default** — the US/default path is untouched; only opt-in. (2) **Q is deliberately excluded** (Cmd+Q quits — a nasty surprise from Ctrl+Q), and **nav keys are untouched** (Mac word-nav is Option+arrow, not Cmd+arrow). Windows redo `Ctrl+Y` is NOT mapped — Mac redo is `Cmd+Shift+Z`, reachable via the Z mapping. (3) **Gate** = `MAP_CTRL_TO_CMD && has_ctrl() && !has_cmd() && !has_alt() && is_remappable_shortcut(vk) && !frontmost_is_excluded()` — so `Ctrl+Alt`/`Ctrl+Cmd` combos and non-set keys pass through unchanged. (4) **Terminal suppression** keeps `Ctrl+C` = SIGINT: `frontmost_is_excluded()` matches the frontmost app's bundle id against a **built-in standalone-terminal list** (Terminal, iTerm2, Alacritty, kitty, WezTerm, Ghostty, Hyper, Warp) plus the user's `--no-remap-apps`. (5) **Embedded terminals (VSCode's integrated TTY etc.) can't be auto-detected** — the frontmost app is the IDE, not a terminal — so they're covered by `--no-remap-apps com.microsoft.VSCode,…` (config `NO_REMAP_APPS`). Trade-off in a listed app: Ctrl stays Ctrl everywhere (integrated-terminal `Ctrl+C` = SIGINT works; editor copy uses Cmd+C, the app's native macOS copy). Helper-process ids prefix-match (`com.microsoft.VSCode` covers `com.microsoft.VSCode.helper.*`). The branch sits **before** the layout-translation branch in `key()` so a remapped key-up isn't swallowed by the layout path's swallow-key-up rule. (Pairs with the `--enable-h264` README/startup nudge from the same CTO feedback — the legacy bitmap path logs "video codec: legacy bitmap path … pass --enable-h264" at startup so "not sure what it negotiated / it's grainy" has an answer.)

  **Resolving "what app is focused right now" in a headless session was the hard part (and needed FOUR signals, last-wins, in `LAST_FOCUS_BUNDLE`).** No single macOS API covers every case under `--virtual-display`/`--capture-primary`: (a) `AXFocusedApplication` polled from a background thread (the existing MRU focus poller) works for normal apps but **returns nothing for an Electron app focused by mouse-click**, and the per-keystroke direct AX call returns `None` on the tokio **input thread** entirely; (b) an event-driven **`NSWorkspace` activation observer** (`init_focus_observer`, registered on the `runloop_thread` because NSWorkspace notifications need a pumped CFRunLoop; the activated `NSRunningApplication` comes straight off the notification `userInfo`, so it's the **main** app id) catches normal click-activation and real app launches — but it does NOT reliably fire for our own AX-driven Cmd+Tab activation (see the fourth feeder below), and an Electron app like **VSCode takes *key* focus without ever *activating*** (its keystrokes land in it, yet it emits no activation and no AX focus change), so the observer never sees it either; (c) the fix that finally caught it is a **click hit-test** (`update_focus_from_click`): on every mouse-down (when `--map-ctrl-to-cmd` is on) we `AXUIElementCopyElementAtPosition` the window under the cursor → owner pid → bundle id, run on the `runloop_thread` (AX is reliable there, not on the input thread), using `self.last_x/last_y` which are already global top-left-origin screen coords. These write `LAST_FOCUS_BUNDLE` last-wins; `frontmost_is_excluded` reads it first (then the direct AX call, then MRU front). (d) A **fourth feeder** (fix `641d887`): our own **Cmd+Tab/Option+Tab** AX activation doesn't reliably post an NSWorkspace activation, so the observer (b) missed it — cycling from an excluded app (terminal/VSCode) to a normal one (e.g. Firefox) left the remap suppressed (Ctrl+T did nothing) until a mouse click refreshed the cell. `commit_cycle_session` now writes the landed app's bundle to `LAST_FOCUS_BUNDLE` directly. Helper pids resolve to the owning app via `bundle_identifier_for_pid`'s fallback (`proc_pidpath` → outermost `.app` → `NSBundle.bundleIdentifier`), so a focused VSCode renderer-helper still reads as `com.microsoft.VSCode`. **Display caveat surfaced during this work:** `--capture-primary` already puts the virtual display at origin (it IS primary), but a window opened *before* connecting stays on the now-captured physical panel and is invisible/unclickable over RDP — press **`Ctrl+Alt+G`** (the gather-windows hotkey; see its dedicated note below) to sweep it onto the visible virtual display, or `osascript … set position of window 1 to {100,100}` / Cmd+Tab to it / open a new window — after which click-focus detection works on it like any other app. Verified end-to-end on mstsc: Terminal/TextEdit/Safari/VSCode (incl. integrated terminal SIGINT vs editor Cmd+C), via both Cmd+Tab and click.
- **Client-resolution auto-adopt (default; `--no-client-resolution` to opt out) MUST live in the acceptor — the Confirm Active capset cannot reveal the client's requested size.** Built 2026-06-12 to kill mstsc's client-side rescale (typing latency + H.264 audio drift when the served resolution ≠ the client display's). The client's own requested resolution exists in exactly one place: the GCC **Client Core Data** `desktop_width/height` of the MCS Connect Initial. The tempting alternative — upstream's `RdpServerDisplay::request_initial_size`, fed from the client's Confirm Active bitmap capset — is a dead end for detection: conformant clients **overwrite their desktop size with the server's Demand Active values and echo those back** (verified in FreeRDP's `rdp_apply_bitmap_capability_set` source AND live: sdl-freerdp `/size:1024x768` echoed our 1512×982; mstsc follows the same `desktopResizeFlag` contract). Worse, upstream `ironrdp-acceptor` parses the Client Core Data and discards everything but the early-capability flags, and Demand Active is sent *inside* `accept_finalize` — before any server-side code can react. So: `vendor/ironrdp-acceptor` (new fork, divergence log inside) gains `honor_client_desktop_size` — in `BasicSettingsWaitInitial` it adopts the client's core-data size (sanity band 200..=8192 per MS-RDPBCGR) into `desktop_size` + the server Bitmap capset BEFORE Demand Active, so the session is negotiated at the client's resolution from the start with **no deactivation-reactivation resize**. (A reactivation-based variant — emit `DisplayUpdate::Resize` as the first update — was built first and discarded: it cost an extra full reactivation per connect and still couldn't *detect* anything for echo clients.) The vendor server forwards the flag (`RdpServer::set_honor_client_desktop_size`, divergence 9); `CaptureDisplay::request_initial_size` then adopts the echoed size into the process-wide `SharedDesktopSize` (capture.rs) that capture, `input.rs` mouse scaling, and the `h264.rs` surface/encoder all read — input reads per-event, h264 pins dims per connection in `setup_locked`. Costs are exactly the documented non-native-capture trade-offs below (full-frame legacy updates; on aspect mismatch the picture is **letterboxed/pillarboxed by default** to preserve the Mac's aspect ratio, `--stretch` opts into fill-and-distort — see the scaling note); that's the accepted deal — the prior workaround was passing `--width 1920 --height 1080` manually. Verified live with sdl-freerdp at 1024×768 (legacy) and 1280×800 + 800×600 (H.264/EGFX, fresh surface per connection, acks flowing); mstsc verification pending a real Windows client. Disabled automatically when `--width`/`--height`/`--hidpi`/`--virtual-display` pin a size.
- **Server-side scaling forces full-frame updates; aspect handling is letterbox-by-default on the auto-size path, stretch otherwise.** Capturing at a configured size ≠ the Mac's native size makes SCK scale internally, and SCK's dirty-rects then come in *source* (native) coords (clients that strictly respect tile coordinates render a black canvas with only the cursor sprite — mstsc/RemoteFx is the worst offender). `capture.rs` works around that by detecting the mismatch up front and skipping dirty-rect emission (full BitmapUpdate every tick — the upstream encoder's framebuffer diff still keeps unchanged-region cost low). For the aspect dimension there are two modes, both with `scales_to_fit=true`:
  - **Letterbox/pillarbox (default on the auto-size path, i.e. client-resolution auto-adopt with no `--stretch`):** `preserves_aspect_ratio(true)` — SCK fits the Mac into a **centered** sub-rect of the output and pads the rest with black bars, so the picture isn't distorted. `input.rs::move_to` then maps client coords into that centered content rect (clicks in the bars clamp to the nearest edge) via the pure, unit-tested `map_client_to_display`; the shared `SharedDesktopSize.letterbox` flag tells it which mode is live. **Verified 2026-06-15 on macOS 26** by dumping a captured frame: a 1512×982 Mac → 1920×1080 client produced a centered 1663×1080 image with **exactly 128 px bars each side** (= `(1920−1663)/2`), matching the input math — so clicks align. (No inverse-`preservesAspectRatio` surprise on 26; if a future macOS flips it, the bars will land on the wrong axis and clicks will skew — re-dump a frame to check.)
  - **Stretch/fill (`--stretch`, or any explicit `--width`/`--height`):** `preserves_aspect_ratio(false)` — source stretches to fill the whole output (no bars), with the old caveat of non-uniform scaling on aspect mismatch (e.g. 16:10→16:9 ≈ 13.5% vertical compression) and `input.rs` mapping linearly across the full frame.

  Cost at non-native sizes either way: higher bandwidth (full frames) and, on **mstsc with `--enable-h264`**, the scaling amplifies its trailing-frame presentation lag (see the flush-burst note) — a Mac whose native resolution already matches the client serves 1:1 with no scaling and is markedly snappier (confirmed live: a 1512×982 MacBook Pro lags into a 1080p mstsc session while an M1 mini natively driving 1920×1080 does not). Prefer native if you can.
- **No server PointerPosition forwarding (intentional).** mstsc and Microsoft Remote Desktop local-predict the cursor from the user's mouse input; any `PointerPositionAttribute` PDU we send arrives one encode-plus-network round-trip late and snaps the cursor back to a stale position on fast moves. The current design (`poll_shape` only, `poll_position` defined but unwired) is deliberately the right one for all interactive use. *Do not* simply wire `poll_position` up — that's the bug, not the fix. The only thing this design misses is Mac-side *programmatic* cursor moves (an app calling `CGWarpMouseCursorPosition`, rare); fixing that properly requires emitting position only when the Mac cursor diverges from where the last RDP mouse event left it and enough time has passed since that event, which needs shared state between `input.rs` and `cursor.rs`.

With `--enable-h264` that same client negotiates AVC420 over EGFX and renders H.264 (verified), which is far better — prefer it for the macOS client.

The 3 s transient is nowhere near 20 s, so a healthy session is no longer dropped; a genuine (rare, unconfirmed) mid-session blackout still recovers, just after ~20 s. **The ~20 s figure assumes the ACTIVE QoE cadence (~8/s); on a STATIC blank the cadence collapses to ~0.3/s and the 160-report count alone would take ~9 minutes — so the established tier has a wall-clock companion branch:** an established session is also declared blank once nothing nonzero has arrived for `MACRDP_BLANK_RECOVERY_ESTABLISHED_MAX_WAIT_MS` (default 30 s, RTT-scaled) *and* at least `MACRDP_BLANK_RECOVERY_ESTABLISHED_WALL_REPORTS` (16) consecutive zeros are in evidence — the report floor is the idle guard (an idle healthy session stops producing frames and therefore QoE entirely; with no zeros accumulating, the branch can never trip on mere quiet). Net bound: a genuine mid-session blackout recovers in ~20 s active / ~30 s+floor static, instead of "eventually, maybe". The wall-clock fast path is also withheld once established (was `!ever_presented`, now `!established`) so a single stray zero can't trip it. **The bar is deliberately HIGHER than `min_render_reports` (3, the few-frame disarm):** a post-reactivation *few-frame flicker* stays BELOW the established bar, so the reconnect-blank escalation is unaffected and still fires in ~3 s — only a session that genuinely showed the desktop for seconds gets the lenient window. `established_min_qoe` is RTT-scaled like `min_qoe_reports`; `established_render_reports` is not (like `min_render_reports`, scaling a presentation-quality bar on a slow link is backwards). Unit-tested (`blank_recovery_re_arms_after_a_relapse_but_only_on_a_long_window`, `blank_recovery_barely_presented_stays_aggressive`). Net: the connect-time reconnect-blank (never-established) is unchanged and aggressive; a mid-session relapse on an established session now needs sustained evidence, so a healthy client's transient zero-EDR windows no longer drop it. **UPDATE 2026-07-26 (v0.9.2) — the 07-22 revocable disarm was a REGRESSION for a client that presents fine but reports zero EDR without ever "establishing"; fixed with a durable connect-time presentation latch.** Reported live: after the v0.9.1 install, a client (LAN, `--capture-primary` + virtual display) **connected, showed the desktop, was fully interactive** — and then got force-dropped every ~50 s, `action=Drop … longest_render_run_before=3/5/14`, ARC reconnecting each time → an endless connect/disconnect loop on a *working* session. Root cause is the exact inverse of the 07-22 first update: that update removed the v0.9.0 **one-way disarm latch** (first nonzero EDR → detector off for the connection) and made the disarm **revocable** to catch a client that reported nonzero-while-black *after* a reactivation. But this client is the mirror image — it **presents fine while reporting zero EDR**, and its nonzero-EDR runs are only 3–14 long, so they **never reach the `established_render_reports` bar (40)** that would grant the lenient window; it stayed on the aggressive path, and each sustained zero window (which for this client is just its normal reporting, not a blank) re-fired the detector and dropped it. QoE decode+render-time is thus **bidirectionally unreliable**: one client class reports nonzero-while-black, another zero-while-presenting, and **no threshold on EDR alone separates them**. The one signal that does: ***when* the nonzero run occurs relative to any recovery attempt.** The reconnect-blank is a *connect-time* failure (black from frame one); a client that produces a sustained nonzero run **before any recovery has fired** genuinely painted the desktop on its own and is not the blank. Fix (`src/h264.rs`): a durable **`QoeEvidence::presented_clean`** latch — set by `on_qoe_metrics` the moment `nonzero_streak >= min_render_reports` **while `blank_recovery_attempts == 0`**, never cleared; `should_blank_recover` returns false unconditionally once it's set (the v0.9.0 one-shot disarm, restored). The `attempts == 0` guard is the linchpin and is what keeps the 07-22 fix intact: the blank client's nonzero-while-black flicker only appears *after* its reactivation (attempts > 0), so the caller **withholds** the latch for it → that client is still recovered by the escalation, exactly as before. Trade-off, stated plainly: a genuine *mid-session* blackout on a cleanly-presented connection is now **not** auto-recovered (it was only ever an unconfirmed case anyway) — the manual **`Ctrl+Alt+Shift+R`** A/V-resync hotkey is the lever for that. The established-tier code is retained but is now rarely the deciding factor (the latch supersedes it for any client that presents at connect). `min_render_reports` is frozen onto the `ConnectionContext` at setup (`ctx.min_render_reports`) because `on_qoe_metrics` only sees the context, not the owning `Gfx`. Unit-tested (`blank_recovery_disarmed_by_clean_presentation`, `blank_recovery_clean_latch_does_not_shield_a_never_presented_blank`); **live-verified that DISABLING the detector (`BLANK_RECOVERY=0`) stops the loop** (confirming the diagnosis), with the latch fix pending live re-verification on the affected client. Do NOT "simplify" the latch by dropping the `attempts == 0` gate or by latching on `max_nonzero_streak` (which survives across attempts) — either one re-breaks the 07-22 blank client. **Side issue surfaced while live-verifying this fix (deferred, NOT in v0.9.2): a blank-recovery reactivation UN-BLANKS the `--capture-primary` physical panel.** Once sessions stopped false-dropping, a *genuine* reconnect-blank heal (the bare core Deactivation–Reactivation) was observed to leave the physical primary panel showing the desktop — the reactivation is a display reconfiguration and macOS resets the panels' gamma on one, exactly like the live-resize case, but the recovery reactivation emits a **same-size** `DisplayUpdate::Resize`, so `sync_virtual_display` early-returns and skips the `reassert_blanking()` the resize branch runs. A first fix (re-assert off-thread + spaced after the same-size reactivation, on branch `wip/capture-primary-reblank-on-heal`) was **flaky** in live testing (the spaced re-asserts don't reliably beat the reactivation's variable-timing gamma reset) and was **reverted** — the un-blank is pre-existing (present since blank-recovery reactivation shipped in v0.8.27) and only *noticed* now, so it is a separate follow-up, not a v0.9.2 regression. The robust fix is almost certainly the same one the gamma-blanking note calls for — a black **shield-window** helper that survives reconfigurations (`--shield-primary` already avoids the whole class) — not more gamma-timing races. Until then, a `--capture-primary` user whose session heals a reconnect-blank may see the physical desktop until disconnect; `--shield-primary` is the mitigation.
- **mstsc holds a ~2-frame AVC420 presentation buffer; the last change before a pause needs trailing "flush" frames (`--flush-frames`, in `capture.rs`).** mstsc only *presents* an H.264 frame once ~2 more frames arrive behind it, so on a static screen the last change (the final keystroke before you pause, a window-to-front) strands in that buffer until something else moves or the periodic keyframe lands — the "typing follows the keyframe" lag. The trap: **ScreenCaptureKit stops delivering frames when nothing on screen changes** (idle samples have no content and are skipped at `capture.rs`), so there is no continuous stream to push the buffer through — raising `--fps` alone does *not* fix it (it only shrinks the per-frame interval). The fix is a **bounded flush-burst**: after each EGFX-accepted frame, `next_update` stashes the BGRA (reused buffer) and arms a counter; its SCK stream-wait is wrapped in `tokio::time::timeout(frame_interval, …)`, so when SCK goes idle the timeout fires and we re-submit the stored frame as a cheap skip-P-frame, `--flush-frames` times (default 4; mstsc needs ≥2; **0 disables**). That drains the buffer within ~2 frame intervals (~33 ms at 60fps), then the stream goes quiet — no always-on cost, and the legacy bitmap path is untouched (the counter only arms on the EGFX path). **Do NOT "fix" this by reinstating idle-frame suppression or relying on a continuous always-on stream** — SCK won't feed one, and suppression strands the trailing frame again (tried and reverted). FreeRDP/Thincast present each frame immediately and need none of this. Verified on M1; periodic `--keyframe-interval` default is 2 s (it self-heals garbled frames but, with the flush-burst, no longer governs typing latency).
- **Resizing/moving the mstsc window drifts audio late — H.264-only (`--enable-h264`).** With H.264, EGFX video frames and the RDPSND audio waves share the *same socket writer* — a single `SharedWriter` (`Rc<Mutex<..>>` over the one TCP connection) cloned per task. Audio rides its own dedicated `mpsc` channel + `dispatch_audio` task (it was carved out of the unified `ServerEvent` channel), but every `audio_writer.write_all` still has to acquire that one shared socket lock — the same lock the EGFX path holds while writing a frame. Legacy bitmaps don't contend the same way (dirty-rect, intermittent, default 15 fps, coalesced through `dispatch_display`), which is why the legacy path is immune. When mstsc freezes the socket during a window resize/move/fullscreen-toggle, `write_all` blocks on the large queued video frames; wall-clock keeps advancing while no audio ships, so the cross-batch audio-lag model in `vendor/ironrdp-server` (`audio_shipped_ms` vs `audio_clock_start`) sees its buffer projection go *negative*, reads it as "client starving," and ships the entire stale backlog late — bloating the client's playback buffer. Each stall adds more negative credit, so without intervention the wave-drop logic stops firing and audio gets *progressively* more delayed the more you resize. Fix (in `dispatch_audio`'s task-local lag loop): when `real_elapsed - audio_shipped > 300 ms` the writer clearly stalled and the queued waves are stale, so resync `audio_shipped_ms` to live; the existing drop-oldest cap then trims the backlog to one `MAX_LAG_MS` (200 ms) of the freshest waves. For a live stream, dropping stale audio is always right — never replay it late. EGFX frames themselves are *not* dropped in dispatch (H.264 inter-frame coding forbids it; they're bounded capture-side by frames-in-flight). FreeRDP/Thincast don't freeze the socket on resize and never showed this. See the `vendor/ironrdp-server` note for the divergence layering (this resync is local-only, distinct from the merged keep-newest PR #1276). **Minimize→unminimize is the same socket-stall class, but the DEFAULT path handles it upstream of the resync:** *mute-on-minimize* (default on; see the `SuppressOutput` note below) mutes RDPSND *and* short-circuits EGFX **at the source** during the minimize — both behind the shared, 1 s-debounced `display_suppressed` flag — so no audio backlog accumulates, and on the un-suppress (restore) edge a forced IDR keyframe resyncs the video; A/V come back in sync with only a brief gap, no resync needed. The 300 ms-deficit resync above is the safety net for when audio keeps *flowing* through a socket stall — **resize/move/fullscreen** (never muted), and **minimize with `--no-mute-on-minimize`** (where the accumulated backlog is dropped-to-freshest on restore instead of replayed late). So on a minimize/unminimize you're normally seeing the mute-gate + restore-IDR, not the deficit resync; the resync only bites when the mute is disabled or the stall isn't a minimize.
- **On-demand A/V resync hotkey (`Ctrl+Alt+Shift+R`) — manual recovery of a session gone stale after a long idle (blank screen + drifted audio).** Built + live-verified 2026-07-17 for mstsc, whose picture blanks and whose audio drifts (client-side audiodg buffering — un-observable from the server, so auto-detection is a dead end; see the WaveConfirm note) after hours idle. The chord is a manual lever the user presses when they *see* the drift, sidestepping the un-observability. Implemented in `input.rs::try_symbolic_hotkey` (caught before the remap/layout branches, Win-key-free so mstsc forwards it regardless of "Apply Windows key combinations", and not a system shortcut on either OS): it sets two crate-global flags (`RESYNC_VIDEO`/`RESYNC_AUDIO`, in `main.rs`) consumed independently — **video:** `capture.rs` forces a clean **IDR keyframe** (`Gfx::force_keyframe`) to repaint the stale presentation; **audio:** `audio.rs` rebuilds its SCK stream via the existing self-heal `continue 'reconnect` (a brief capture gap lets the client's downstream backlog drain + re-baselines wave timing — the same effect as a minimize→unminimize). **DESIGN DECISION — video uses a forced IDR, NOT the full core Deactivation–Reactivation, and it's load-bearing.** The reactivation (`Gfx::request_reactivation`, the blank-recovery lever) *did* un-blank, but on the `--virtual-display`/`--capture-primary` headless path it **cascades into a visible session re-cycle** — the reactivation re-mods the virtual display → trips the #155 live-resize surface reset (`reset_for_live_resize`) → a `SessionTracker` teardown + `CapturedPrimary::drop` + a headless re-capture → a ~1–2 s reconnect **flicker** (all confirmed in the log: `SessionTracker::leave/enter`, "client disconnected/connected", `virtual display re-moded`). The IDR is far lighter and un-blanks the *stale-presentation* idle-blank with **no session re-cycle and no flicker** (LIVE-VERIFIED on real mstsc: un-blanked smoothly, audio resynced, zero flicker; the log shows *only* the three resync markers, none of the re-cycle events). `request_reactivation` is kept `#[allow(dead_code)]` as the escalation for a *surface-retention* blank an IDR can't clear (a future IDR-first-then-reactivate-if-still-blank; not needed so far). Log markers (`macrdp.log`, not the `[usb2]` err.log): `on-demand A/V resync hotkey`, `forcing an IDR keyframe`, `rebuilding audio capture stream`. The audio flush is best-effort for the client audiodg (verified to resync live); if a future client doesn't drain on the SCK-rebuild gap, the documented next levers are a longer mute-cycle or an RDPSND format re-negotiation.
- **Honoring `SuppressOutput` is required to avoid input-lockout on minimize→refocus — but three arming gates are also required, or mstsc freezes on connect / reconnect / stutters under heavy local CPU/IO.** Reported + fixed 2026-05-26 (v0.5.47, debounce + mute-on-minimize landed in v0.5.48). Original bug: minimize mstsc for several minutes with H.264 video flowing → refocus → desktop frozen, audio skips, video speeds up to catch up. Root cause: vendor server was logging `SuppressOutput` as `Unexpected share data pdu` and ignoring it; we kept streaming 60 fps of EGFX frames into a minimized client, which accumulated them, and on refocus mstsc had to chew through the backlog before it could present the current frame — its input dispatch was busy the whole time, ~several seconds of total UI lockout. Fix: vendor server pattern-matches `SuppressOutput` / `RefreshRectangle` and toggles a shared `Arc<AtomicBool> display_suppressed` (exposed via `set_display_suppressed_handle`); `capture.rs::next_update` checks the flag and short-circuits SCK pull + encode + ship while it's set; on the true→false edge a one-shot IDR keyframe is forced so the client resumes from a clean reference frame. **Three arming gates are non-obvious and load-bearing:** (1) **first-EGFX-frame gate** (`first_egfx_frame_sent` in `ScreenCaptureUpdates`) — mstsc's normal connect handshake includes a `SuppressOutput { None }` *before* its display surface is fully initialized; honoring it then leaves mstsc with a half-init'd surface that doesn't recover on un-suppress and the desktop never paints. FreeRDP doesn't issue suppress during connect and was never affected, which is why blanket honor "worked on FreeRDP." Gate the gate so it's only respected after the first EGFX-accepted frame ships. (2) **per-connection reset of the flag** (in `ScreenCaptureUpdates::start`) — the `Arc<AtomicBool>` is owned by the server and survives across disconnect/reconnect; if the previous session ended with it `true`, the *next* connection arms its first-frame gate, immediately reads the stale `true`, and freezes the new session. Reset to `false` at the top of every `start()` call. (3) **per-reader debounce (`SUPPRESS_DEBOUNCE = 1 s`, identical in `capture.rs` and `audio.rs`)** — under heavy local CPU/IO (cargo build, big disk I/O) mstsc emits transient `SuppressOutput { None }` → `RefreshRectangle` pairs tens of ms apart to throttle the server when its receive queue grows. Reacting to those rapid flaps thrashes both the video gate and the audio mute, producing audible stutter and visible video hiccups even though no real minimize occurred. Each reader maintains a local `Option<Instant>` "first observed suppress=true" timestamp and only engages the gate once `elapsed >= SUPPRESS_DEBOUNCE`. Real minimizes (seconds-to-minutes) cross that threshold easily; backpressure flaps don't. Don't remove any of the three gates without re-testing first-connect, reconnect-after-disconnect, long-minimize, AND cargo-build-while-watching-YouTube on mstsc. Mute-on-minimize is default-on (`--no-mute-on-minimize` to disable) and uses the same shared flag + same debounce so audio and video stay coherent through transients.
- **EGFX-over-UDP (`--udp-migrate-egfx`) + minimize/restore froze the picture until reconnect — fixed by proactively de-migrating to TCP on the un-suppress edge.** Reported + fixed 2026-06-29 (PR #99). Symptom on real mstsc/WiFi: with EGFX migrated onto the reliable UDP tunnel, minimizing the mstsc window then restoring it left the **video frozen** (audio, on TCP, resumed fine) until a full disconnect + reconnect to a *fresh* mstsc; an EGFX-on-TCP-from-start session (`UDP_MIGRATE_EGFX=0`) handled the same minimize/restore cleanly. Root cause: once the EGFX DVC has been **Soft-Sync-migrated onto the UDP tunnel**, mstsc's surface doesn't survive the SuppressOutput→restore cycle, and the wedge **watchdog** (above) only de-migrates *reactively* — 3–6 s after restore (confirmed in the log, `since_ack_ms=6641`), *after* we've already shipped the restore frames into the now-stale post-minimize tunnel, by which point switching the transport is too late to heal the client surface. Fix: on the un-suppress (restore) edge, if EGFX is currently on the reliable UDP tunnel, **proactively de-migrate to TCP BEFORE shipping a single frame back into the tunnel** (`Gfx::demigrate_on_resume`, called from `capture.rs`'s existing `was_suppressed` resume edge), so the forced restore-IDR lands over TCP — which mstsc renders across minimize exactly like an EGFX-on-TCP-from-start session. It mirrors the watchdog's de-migrate steps (force IDR + reset the lag baseline + set the `demigrated` latch / `demigrate_request`), is **one-way per connection** (a reconnect starts fresh on UDP), and is a **no-op on the TCP/default and lossy paths** (gated `egfx_on_udp && !egfx_on_lossy` → those paths byte-unchanged). **Verified live on real mstsc** (`--udp-migrate-egfx --bitrate 6 --adaptive-bitrate`): minimize→restore → video comes back; log shows `client resumed from minimize while EGFX was on the reliable UDP tunnel — proactively de-migrating to TCP`. This confirms the freeze was the *transport*, not the unfixable mstsc reconnect-blank surface bug. (Distinct from the SuppressOutput arming-gates note above, which is the always-on minimize handling; this is the UDP-specific layer on top.)
- **Minimizing mstsc for minutes then refocusing → audio plays back 1s+ late, and we can't see it from the server side.** Reported 2026-05-26. When mstsc is minimized while RDPSND audio keeps flowing (e.g. YouTube playing on the Mac while the user does other Windows work), Windows' audio mixer (`audiodg.exe`, a separate process) appears to throttle playback while continuing to drain mstsc's network buffer; on refocus, the buffered backlog plays out — audio lags by however much accumulated. **`WaveConfirm` is not a usable signal for this** — investigated 2026-05-26 by surfacing every confirm via `RUST_LOG=ironrdp_rdpsnd=debug`. Confirms flow continuously through minimize at full ~46/sec rate (one per ~21 ms wave), with no gaps or slowdowns. That means mstsc emits `WaveConfirm` on *arrival/queue* into its dispatch (it has received and forwarded the wave to audiodg), not on *playback completion through speakers*. The actual buffering happens downstream in audiodg, which the RDP stack does not observe. A server-side wave-confirm tracker (the obvious "detect client playback lag" design) would see all confirms arriving fine and never trip its drop logic; it cannot fix this. **Do NOT try to fix this with a `WaveConfirm`-based playback tracker** — verified dead-end. The two realistic options if this becomes worth fixing: (a) heuristically throttle wave emission while mstsc has sent `SuppressOutput` (correlates with minimize but not 1:1 — see the `Unexpected share data pdu` warnings in logs); (b) accept as a Windows audio-mixer behavior we cannot see from RDP and document the limitation (current choice).
- **Why mstsc audio is mostly smooth while FreeRDP/Thincast are choppier — RESEARCHED 2026-07-18 (three-agent primary-source pass: FreeRDP 3.30.1-dev source, MS-RDPEA spec, Thincast licenses page). The clients have opposite buffering philosophies, and macrdp's own config stacks the deck further.** (1) **Transport privilege:** with `ENABLE_AAC=1` + `ENABLE_LOSSY_AUDIO=1`, LAN mstsc gets AAC on a dedicated lossy-UDP flow with 1+1 dup — decoupled from video. FreeRDP structurally can't: its client answers every Server Initiate Multitransport Request from a hardwired `multitransport_no_udp` stub with `E_ABORT` (re-verified on master 2026-07-18; nothing UDP ever merged, the RDPEUDP2 prototype stayed out-of-tree), so FreeRDP/Thincast audio always rides the video-contended TCP socket behind the single `SharedWriter` lock. (2) **Buffering:** **mstsc** plays waves via an **unbounded legacy waveOut queue** — strictly in order, no drop/resync, late waves play *late* rather than glitching (the same queue that causes the minimize-backlog quirk above; the engine/audiodg period buffer itself is shallow ~10 ms — the depth is mstsc's own WAVEHDR backlog). **FreeRDP** is the opposite by explicit design: `rdpsnd_treat_wave` plays each wave synchronously on arrival (no jitter buffer at all), and `rdpsnd_detect_overrun` actively **caps pending audio at ~2 wave-durations (+`latency:` arg, default 0 → ~40 ms for our 21 ms waves) and silently DROPS the excess** (DEBUG-level log only); an underrun is just logged — a late wave is an audible gap. **Caveat: the overrun dropper EXEMPTS AAC** (can't size compressed formats — `WAVE_FORMAT_AAC_MS` returns "never drop"), so with `--enable-aac` a server-side over-feed to FreeRDP is NOT client-trimmed. (3) **Codec:** Thincast is **PCM-only** (its third-party-licenses page ships OpenH264 + libswscale but no libavcodec/fdk-aac/faad2 — corroborating our 2026-05-30 wire observation `client_formats=1`), so ~1.4 Mbit/s PCM contends with H.264 frames for the writer; FFmpeg-DSP FreeRDP builds decode our AAC (AAC is deliberately the one codec `ffmpeg_codec_is_filtered` never filters; raw AUs need no extradata). **The actionable client-side knob is `/sound:latency:<ms>`** (e.g. `latency:100`) — it raises FreeRDP's overrun cap AND (Pulse only) requests a real sink buffer (`tlength` + `ADJUST_LATENCY`), emulating mstsc's smoothing at the cost of latency. **`/audio-mode` is NOT a buffering knob** — it's routing only (0=redirect, 1=leave-on-server, 2=none; note FreeRDP's own help text has the numerics swapped — the names are authoritative). Bonus finding: FreeRDP sends **two** WaveConfirms per wave and the second's timestamp **includes the backend-reported render latency** (Pulse `pa_stream_get_latency`, ALSA `snd_pcm_avail_delay`) — unlike mstsc's consume-time confirms, a server-side latency estimator DOES get real render latency from FreeRDP; a possible future signal. Rate note: FreeRDP opens the sink at the stream rate (44.1 kHz) and lets the OS sound server do any 44.1→48 conversion — FreeRDP itself never resamples playback.

- **`--virtual-display` on mstsc: large legacy frames are strip-split, a release build matters, and the cursor is warped home on disconnect.** Verified 2026-06-02 against remote mstsc. One gotcha plus two fixes: (1) **Legacy big-frame blank on mstsc — FIXED by strip-splitting.** A virtual display is captured 1:1, so `force_full_frame` is *false* — the full WxH paint is sent once on the first frame, then dirty-rects. The bitmap encoder (`vendor/ironrdp-server/src/encoder/bitmap.rs`) packs that whole rect into ONE update PDU (one RLE rectangle per ~`65535/(w*4)` rows), and mstsc has a per-update size/rect-count limit: it renders a single ~1280×720 (≈0.9 MP, ~60 rects) update but DROPS a 1920×1080 (≈2.1 MP, ~135 rects) one, so the desktop never painted (only the ticking-clock dirty-rect rendered → "almost blank, only the menu-bar clock visible"). Fix: `capture.rs::split_strips` splits any emitted rect into horizontal strips ≤ `MAX_BITMAP_UPDATE_PIXELS` (= 1280×720, the proven-good size) so each becomes its own smaller, renderable update. Verified: 1920×1080 legacy vdisplay now renders the full desktop on mstsc. (`--enable-h264` is still preferable for bandwidth/quality, but legacy no longer blanks.) (2) **Debug builds make mstsc reset.** `cargo run` (unoptimized) encodes ~400 ms/frame; that stalls the socket and mstsc resets the connection right after the first EGFX frame ("Connection reset by peer"). A release build (`cargo build --release`, ~20× faster encode) holds the connection and renders cleanly. Always test mstsc on a release build. (3) **Cursor-stranding fix.** During a vdisplay session `input.rs::move_to` posts the cursor into the virtual display's slot of the global coordinate space (off every physical panel). - **AAC audio (`--enable-aac`) is raw access units with `cbSize=0`, and the AudioToolbox pull loop has an end-of-stream trap.** Four hard-won facts behind `src/aac.rs`: (1) **Wire format.** The `WAVE_FORMAT_AAC_MS` (0xA106) payload over RDPSND is **raw AAC-LC access units** — object type 2, 1024 frames/AU, NO ADTS/LATM headers and NO in-band AudioSpecificConfig. The AAC `AUDIO_FORMAT` is advertised with `cbSize=0` (no HEAACWAVEINFO blob); the decoder derives its config from the WAVEFORMATEX rate/channels. Verified against FreeRDP's server (`server/common/server.c` advertises 0xA106 with `cbSize=0`; `dsp_fdk_impl.c` configures fdk-aac `AOT=2`, `TRANSMUX=0`). AudioToolbox's `kAudioFormatMPEG4AAC` encoder emits exactly this, so the magic cookie / ASC it can produce is intentionally never sent. (2) **The EOS trap.** `AudioConverterFillComplexBuffer`'s input proc returning `noErr` with zero packets is read by AudioConverter as *end-of-stream* — after the first batch the converter refuses all further input and audio dies after ~3 packets. The proc must instead return a **non-zero sentinel status** (`INPUT_EXHAUSTED`) to mean "no more data this batch"; `encode` treats that as a clean break, leaving the converter's internal <1024-frame remainder buffered for the next call. (3) **The vendored audio-lag model is byte-based and had to learn duration.** `vendor/ironrdp-server`'s `dispatch_audio` task converts each wave's *byte length* to ms via `BYTES_PER_MS = 176.4` (PCM-specific). A ~120-byte AAC AU is ~23 ms, so that math reads the projected client buffer as near-empty and silently disables the drop-oldest/resync lag control. Fix: `AudioWave` gained a third field `Option<f64> duration_ms`; AAC passes `Some(1024/44100*1000 ≈ 23.22)`, PCM passes `None` (unchanged). See vendor divergence (8). (4) **~40–50 ms priming latency** is why it's opt-in — PCM stays the LAN default. Clients without an AAC rdpsnd decode path fall back to PCM automatically because we advertise both, AAC first, and `start()` picks the first mutually-supported format. (MS-RDPEA notes AAC implies unreliable-UDP DVC transport, but RDPSND over the static TCP channel carries AAC fine — FreeRDP's server does the same.) **Client-support matrix (verified 2026-05-30).** Whether a FreeRDP-family client decodes AAC is build-dependent, and it's NOT just the `WITH_FDK_AAC`/`WITH_FAAD2` flags: `freerdp_dsp_supports_format` first delegates to the **FFmpeg DSP backend** when `WITH_DSP_FFMPEG=ON`, and there AAC is the *only* compressed RDPSND codec NOT filtered out (`ffmpeg_codec_is_filtered` hard-drops MP3/GSM/ADPCM/G.711 unless `WITH_DSP_EXPERIMENTAL`, but returns false for `AV_CODEC_ID_AAC`). So a stock Homebrew `sdl-freerdp` 3.26.0 — `WITH_FDK_AAC=OFF WITH_FAAD2=OFF` but `WITH_DSP_FFMPEG=ON WITH_FFMPEG=ON` — **advertises AAC and decodes our raw AUs cleanly via FFmpeg** (live test: server `use_aac=true client_formats=2`; client log `Opening device with format WAVE_FORMAT_AAC_MS [backend WAVE_FORMAT_PCM]` then `rdpsnd_treat_wave` on every ~280-byte AU with zero `aacDecoder_DecodeFrame failed`). The feared raw-AU "needs ASC as extradata" wrinkle did not materialize — FFmpeg's AAC decoder handled it. By contrast the **Thincast** build tested advertised only PCM (`client_formats=1`) — its rdpsnd path has no AAC decoder — so it (correctly) falls back to PCM; that's a Thincast build limitation, not a server bug. mstsc decodes AAC natively. Practical upshot: AAC is effectively the only non-PCM RDPSND codec any modern FreeRDP build will take, and we already advertise it; there is no other compressed format worth adding for the fallback clients. (Test note: on macOS use `sdl-freerdp`/`wlfreerdp`, NOT `xfreerdp` — the latter is the X11 client and fails `pre_connect` with no `$DISPLAY`.)
- **RDPSND `wFormatNo` indexes the CLIENT's format list, not the server's — latent bug exposed by AAC.** `start()` returns the `wFormatNo` stamped onto every Wave2 PDU, and the client resolves the wave's codec as `ClientFormats[wFormatNo]` — an index into the *Client Audio Formats PDU the client sent back*, which is its supported subset of our server list, compacted in server order. FreeRDP/Thincast hard-reject `wFormatNo >= NumberOfClientFormats` (`rdpsnd_recv_wave2_pdu` / `rdpsnd_recv_wave_info_pdu`) and drop the wave silently — no audio. For years `audio.rs::start()` returned the *server*-list index and it worked only because we advertised a single format (server idx == client idx == 0). The moment `--enable-aac` made the list `[aac, pcm]`, a PCM-only client (Thincast advertised `client_formats=1`) got `wFormatNo=1` for PCM's *server* slot while its own list had PCM at index 0 → `1 >= 1` → every wave rejected → silent. mstsc happened to keep working because it lists AAC at index 0 in both. Fix: choose the format by server preference (AAC-first, so we know what to encode), then return that chosen format's position in `client_format.formats` (the client list). **Do NOT revert to the server-list index** — the old code comment claiming "wFormatNo indexes the server list, client-list index causes wrong pitch" was a misdiagnosis: wrong pitch only happens if you pick the format by scanning the *client* list first and matching loosely (you can select a different rate than you encode). Picking via server preference and *then* translating that exact format to its client-list slot is correct for both mstsc and FreeRDP, because the index always points at the format actually being sent. Verified: Thincast/FreeRDP `use_aac=false` PCM fallback was silent before, plays after.

(3) **`force_full_frame` must treat backing as native** — it compares the configured size against `display.width()` (SCK points); a backing-size capture (3024 ≠ 1512) would wrongly force full frames + warn. Fixed to accept EITHER the point size or the backing size as a 1:1 native capture (dirty-rects stay valid; the EGFX/H.264 path submits full frames regardless so it's unaffected either way). (4) **Do NOT scale the cursor.** SkyLight's `SLSGetGlobalCursorData` already returns the pointer at backing/physical pixels (≈28 px on Retina) and RDP clients render pointer bitmaps at 1:1 device pixels regardless of session resolution — so the same bitmap is correct at points OR backing. An attempt to upscale it by the backing/points ratio made the pointer 2× too big; reverted. An *opt-in* `--cursor-scale` multiplier (default `1.0` = native size, no resize) was later added for comfort: some clients draw the pointer at 1:1 device pixels while upscaling the desktop image to their window, which makes the native-size pointer look small, so bumping it (e.g. `2.0`) enlarges the bitmap **and** its hotspot together via an alpha-weighted area resample (`cursor/mod.rs::scale_cursor`) — the hotspot stays exact at any value. An auto-scale-to-points *default* was tried during this work and rejected: the user preferred native size, and a separately-reported Retina "cursor shrank / hotspot off" turned out to be a **stale mstsc pointer cache** (cleared by reconnect / close+reopen), not a server scaling bug — so the default still does NOT scale. (5) **The lag is the client, not the server.** VideoToolbox encodes 3024×1964 in ~10 ms/frame (99 fps of headroom, under the 16.67 ms/60fps budget) — the server keeps up and doesn't drop frames. But **mstsc decodes 4× the pixels per frame and, with its documented 2-frame presentation buffer (now of 4×-bigger frames), feels laggy at HiDPI**; Thincast/FreeRDP decoders stay snappy. This is a client characteristic, documented not fixed — which is why `--hidpi` is opt-in and best paired with a capable client. **Pooling the per-frame `CVPixelBufferCreate` was tried and is NOT worth it (2026-06-21).** The suspected lever — the per-frame ~9 MB NV12 `CVPixelBufferCreate` in `videotoolbox.rs::encode_frame` — was replaced with a per-encoder `CVPixelBufferPool` (IOSurface-backed, via `IOUSBHostControllerInterface`'s sibling `CVPixelBufferPoolCreate`/`…CreatePixelBuffer`) and benchmarked A/B against the per-frame path (an `MACRDP_H264_NO_POOL` toggle gated the fallback). Result: **~parity** — submit cost 4.0/4.1 ms (1080p) and 11.2/11.1 ms (HiDPI), throughput 233/231 fps (1080p) and 93/91 fps (HiDPI), i.e. ≤2% and within noise. Why: the per-frame create is **not** the bottleneck (the allocator + CoreVideo cache recycle the freed buffer warm), and the path is **fill-bound** — dominated by the vImage BGRA→NV12 conversion (~11 ms ⇒ ~90 fps at HiDPI), which pooling doesn't touch. The change was **reverted** (correct but no measured gain; project favors minimal changes). **Do NOT re-attempt CVPixelBuffer pooling for speed** — the encode path's real ceiling is the vImage fill + the HW encoder, not pixel-buffer allocation. (And neither moves the client-side decode floor.)

- **Smart-card redirection is a user-space PC/SC IFD handler, NOT a kext — and that's the right layer, not a compromise.** The recurring "why not a kernel driver?" question. The decision falls out of *what layer the redirection lives at*: MS-RDPESC carries **PC/SC calls** (`SCardConnect`/`SCardTransmit`/APDUs), not raw USB packets, so the macOS side just needs a *virtual PC/SC reader whose backend is the network* — which is exactly what an **IFD handler** is. There is no physical device to model on the Mac, so there is nothing for kernel code to do. macOS's smart-card stack (`com.apple.ifdreader` / slotd / CryptoTokenKit) is **user-space by design** and loads third-party reader drivers as plain **dylibs** (the IFDHandler v3.0 C ABI) from `/usr/local/libexec/SmartCardServices/drivers/` — Apple's documented, supported plug-in point, needing **no special entitlements** to reach the PC/SC stack. A kext would be the *wrong* layer (kernel code is only needed for **raw-USB passthrough** — modelling the physical reader as a kernel USB/HID device, a different and much lower-level feature; the earlier `jiegec/usbip` raw-USB detour is what confirmed *generic* USB redirection needs kernel-level code — historically a kext, and on modern macOS/Apple Silicon either a **DriverKit System Extension** or a **user-space virtual USB host controller** via `IOUSBHostControllerInterface` driving Apple's built-in `AppleUSBUserHCI` provider ("UserHCI" — no kext, no dext; binary forensics of VirtualHere's client, `nm`/`strings` showing `IOUSBHostControllerInterface`/`IOUSBHostCI*StateMachine`/`AppleUSBUserHCI`/`OSX11ClientDriver.mm`, suggest this is the route it takes — note the device is still registered in the IORegistry by Apple's *own* kernel HCI provider, just driven from user space, so it's "no third-party driver," not "no driver at all"; using it needs the managed entitlement `com.apple.developer.usb.host-controller-interface` — Apple-granted *on request* via Feedback Assistant + Team ID, and crucially NOT the contentious `com.apple.developer.driverkit.transport.usb` that stalls `usbipd-mac`. See **`docs/usb-redirection-feasibility.md`** for the full feasibility writeup if generic USB redirection is ever pursued) — which is precisely why the smart-card "device-class" route was chosen instead to stay protocol-only) **and** an expensive one: kexts are deprecated, and loading one on modern/Apple-Silicon macOS needs kext-signing (a case-by-case Apple grant) or SIP disabled, plus user approval + a **reboot**; the sanctioned successor — **DriverKit / System Extensions** — is no better here, for three reasons: (1) a dext needs **restricted entitlements you can't grant yourself** — the base `com.apple.developer.driverkit` plus a transport family like `com.apple.developer.driverkit.transport.usb`, requested from Apple with a written justification (they can decline) and baked into a **provisioning profile signed against a paid Developer account** — so no ad-hoc signing, no file-copy install; (2) it ships **as a System Extension embedded in a notarized `.app`**, activated via `SystemExtensions.framework` with a System-Settings approval prompt (plus reduced-security friction on Apple Silicon) — a far heavier install/first-run flow than dropping a bundle into the drivers dir; (3) most fundamentally **it's the wrong layer** — DriverKit models *real hardware transports* (USB/PCI/HID/serial/net/block), there is **no CCID / PC-SC / smart-card family** — the USB family (USBDriverKit, on the IOUSBHost classes) is the closest, and that's what generic USB-over-IP uses to present a remote device (generic USB-over-IP DOES synthesize a virtual USB device — whether via a dext, or (as VirtualHere's client appears to, per its symbols) a user-space virtual host controller on `IOUSBHostControllerInterface`/UserHCI; an earlier version of this note wrongly said synthesizing a virtual device wasn't possible, and a later one wrongly pinned VirtualHere on DriverKit). To use it for smart cards you'd drop down to that USB layer and **emulate a physical USB CCID reader at the transport level** — exactly the raw-USB route we avoided, far more code (USB descriptors, CCID class protocol, bulk endpoints) — only to rely on macOS's built-in CCID/PC-SC stack to surface the **same PC/SC reader the IFD handler gives you directly**, one layer up. So DriverKit is pure overhead: permission gymnastics + a hardware-transport abstraction, to reach where the user-space IFD handler already sits with a file copy and no entitlements. Being a small user-space dylib is also what let the handler be written **from scratch (MIT/Apache)** instead of shipping the GPL `vpcd` from vsmartcard, and installs as a normal file copy (one admin prompt) rather than a kernel module. The **one** cost accepted from this route: macOS loads a third-party IFD driver **only on a USB hotplug** matching the bundle's VID/PID, so a headless server needs a dummy USB dongle permanently attached as a trigger — minor next to the signing/SIP/reboot/entitlement tax a kext would impose. (Unrelated: the "no root, no kext, no FUSE" notes elsewhere are about the **drive-redirection NFS mount**, a different feature.)
- **Generic USB redirection (`--enable-usb-redirection`, EXPERIMENTAL) — the hard-won traps.** macrdp presents a client-redirected USB device via the public `IOUSBHost` **UserHCI** virtual host controller (`src/usb_redirect/usb_spike.m` is the quarantined SPI boundary; `src/rdpeusb.rs` divergence 16 is the URBDRC transport). Verified: a redirected flash drive mounts on the Mac. Gotchas that cost real debugging time:
  - **It NO-OPS without the entitled build.** The UserHCI controller needs `com.apple.developer.usb.host-controller-interface`, which only exists in the signed+provisioned bundle. A plain `cargo build` logs `controller unavailable (needs the entitled build)` and presents nothing — so all live testing is on the entitled `.app` (`PROVISION_PROFILE=…macrdpprov2.provisionprofile …make-app.sh`).
  - **You cannot test bulk/mount from a macOS *client* (loopback).** macOS libusb can't kernel-detach a mass-storage device to claim the interface (`LIBUSB_ERROR_ACCESS`), and every bulk transfer needs a claimed interface. So the loopback proves enumeration/encoding but not the mount — you need a **Linux or Windows** client. The proven rig: **UTM-QEMU** Ubuntu + FreeRDP `/usb:...`, with a **USB-2.0 hub** in the path (QEMU passthrough of a USB-3 SuperSpeed device fails `Invalid ep0 maxpacket: 9`; the hub forces high-speed) and a guest `udev MODE=0666` for libusb.
  - **`status=1` in the `[usb2]` log means SUCCESS, not stall.** `IOUSBHostCIMessageStatusSuccess`'s raw enum value is 1; the completion log prints the raw value. A stall is a *different* value. Don't read `status=1` as an error (this genuinely misled a diagnosis).
  - **A device reset destroys+recreates the endpoint at the SAME key** (new Active object, fresh ring) while an in-flight completion still points into the OLD freed ring → SIGSEGV in the completion memcpy. The liveness (`endpointState==Active`) check is insufficient because the *new* endpoint is Active; the fix is **endpoint-OBJECT identity** — the completion captures the endpoint object at raise time and drops itself if `endpoints[key]` was replaced. A mass-storage Bulk-Only Reset (`bmReq=0x21 bReq=0xff`) triggers exactly this.
  - **A client can announce ONE physical drive TWICE** with instance ids differing by a byte (FreeRDP does this — `…d31`/`…d32`). Presenting both spins up two virtual drives that **duel over the single client device** → conflicting SCSI, 10 s timeouts, failed mount. So `drive_device` dedups on the device's **stable hardware identity (`VID:PID:bcdDevice`)**, not the client's per-announce instance id. (Two identical-model drives collapse — true multi-device needs iSerialNumber, deferred.)
  - **A streaming bulk-IN endpoint (webcam) needs URB *depth* — serving one read at a time starves it.** macOS double/triple-buffers a streaming bulk-IN endpoint (it queues several concurrent reads so the device's pipe never runs dry), but the UserHCI ring exposes only ONE transfer (the head) at a time — `currentTransferMessage` advances only on `enqueueTransferCompletionForMessage:`, there is no peek-ahead. Forwarding just the head **serially** → the device produces `moved=0` and macOS destroys the endpoint + retries the COMMIT→read→timeout loop forever; forwarding the same head **repeatedly** (the old "supersede" behaviour) → the device gets depth but half the completions are dropped (a bulk-IN pipe is a stream) → corrupt, no picture. Fix (`usb_spike.m`) = a **bulk-IN read-ahead engine**: on the re-queued-head signal AND a large read (`readLen >= 512`, so 16-byte interrupt polls stay serial), keep `MACRDP_USB_PREFETCH_DEPTH` (default 4; `1` disables) concurrent `bulk_transfer_in` reads in flight to the client — **decoupled from the ring** — buffered in **sequence order** (`MacrdpPrefetchRead.seq` + a reorder map, so out-of-order client completions can't scramble frames) and handed one chunk per ring TRB as it becomes the head. Same UAF guards (endpoint-object identity + Active) on every `msg` write; `tearDownStream` on EndpointDestroy. **Gated on the transfer's READ LENGTH — `isBulkIn` requires `normalReadLen >= 512` in the `walkEndpoint:` gate itself, so a webcam's tens-of-KB streaming reads engage while an HID interrupt poll (≤ `wMaxPacketSize`, e.g. 64 B) stays serial (see the next bullet for the full v0.8.30→0.8.35 saga — the read length is the ONLY reliable discriminator; neither the endpoint address nor the wire-declared `is_bulk` flag separates a streaming bulk pipe from an interrupt one).** No Rust change to the transfer path (the URBDRC/`UsbHandle` side is already per-token concurrent). Verified live: A4Tech `09da:2692` streams **smooth** video over FreeRDP. Log marker: `bulk-IN read-ahead engaged ep=0x82 depth=4 readLen=…`.
  - **Stall watchdog (added 2026-07-17, LIVE-VERIFIED same day on FreeRDP + a bulk webcam).** The read-ahead engine delivers strictly in **sequence order**, and an errored/short completion still fills its seq slot (an empty chunk) so `drainReorder`'s reorder cursor advances past it — robust. **But a completion that NEVER comes back is a permanent gap**: `drainReorder` can't advance past a missing seq, so the ring head macOS presented sits unfed forever and the **video freezes while the rest of the session (a separate channel) keeps working** — the reported "webcam freezes after a while, desktop fine" symptom. This is triggered **client-side**: the real camera stalls on the FreeRDP host (Linux **USB autosuspend**, a `uvcvideo` timeout, or bandwidth starvation), so its pending bulk-IN URBs there just hang and never complete, so macrdp's outstanding prefetch reads never resolve. There was **no timeout on a missing seq**, so the freeze was permanent until the device was re-attached. Fix (`usb_spike.m`): a `dispatch_source` timer on the interface's serial queue (so it touches stream state with the same serialization as the completion path). `MacrdpBulkStream.lastProgressNs` is stamped on every `drainReorder` advance; a stream is wedged when macOS is waiting on a ring head (`pendingHead != NULL`) but no in-order data has arrived for `MACRDP_USB_STREAM_STALL_MS` (default **3000**; **0 disables**; `config.env` key `USB_STREAM_STALL_MS`, alongside `USB_PREFETCH_DEPTH` — both bridged in `args_from_config` since they're `getenv`-read in `usb_spike.m`, which a plist `EnvironmentVariables` edit + `kickstart -k` wouldn't apply). Recovery: complete the waiting head with a zero-length read (`moved=0` → macOS treats the endpoint as starved and re-COMMITs) then `tearDownStream` so read-ahead re-engages fresh once the client resumes — turning a **transient** host-side stall into a self-recovering hiccup. A **permanently** dead camera (host-side unplug) becomes a bounded ~3 s re-COMMIT retry loop (logged each time) rather than a silent freeze, and resumes automatically if the camera returns; even a false positive is self-correcting (just a re-COMMIT blip). The root-cause *trigger* is still client-side — the real fix for *why* it stalls is on the FreeRDP host (disable autosuspend for the cam, check `dmesg` for `uvcvideo`/USB-reset lines) — this only makes macrdp *resilient* to it. `NULL`-progress detection is gated on `pendingHead != NULL`, so a quiescent stream (macOS not asking) is never touched. Log marker: `bulk-IN read-ahead STALL ep=0x… — no in-order data for …s … re-COMMITs`. **LIVE-VERIFIED 2026-07-17** (A4Tech `09da:2692` over FreeRDP, `USB_STREAM_STALL_MS=1500`): a client-side hiccup (`kill -STOP`/`-CONT` on FreeRDP) froze the stream; the watchdog fired at ~1.7–2.2s, macOS re-COMMITted, read-ahead **re-engaged ~0.5–2.2s later, and the video resumed in Photo Booth** — no disconnect, no crash, no manual action. A *terminal* stall (the cam fully dying) was also observed and handled gracefully: STALL → re-COMMIT → the device disconnected (`status=11`) ~40s later → clean fresh re-enumeration (nothing to recover to, correctly).

    ```objc
                    && msg_type(msg) == IOUSBHostCIMessageTypeNormalTransfer;   // ← WRONG
    ```
    which an **interrupt-IN pipe also satisfies** (an HID input-report endpoint is likewise a non-EP0 IN endpoint carrying a `NormalTransfer` — only *isoch* is a distinct msg type). macOS **double-buffers interrupt endpoints too**, so its re-doorbell of the still-unadvanced ring head sent the gamepad into `engageStream:` instead of the plain "skip the duplicate — the outstanding transfer's completion re-walks" path. (1) **The `.systemextension` bundle filename must equal its `CFBundleIdentifier`** — otherwise `OSSystemExtensionRequest` fails with *"unable to find any matched extension"* and the request never even reaches `sysextd`. (It also needs `CFBundleSupportedPlatforms`, which Xcode injects and a hand-assembled bundle must supply.) (2) **`CMIOExtensionClient.signingID` is the literal string `"unknown"`** for every client — it is NOT the code-signing identifier — so producer authentication on the sink is impossible, and worse, an `authorizedToStartStream` that returns `false` surfaces to the producer as a bogus **`CMIODeviceStartStream` OSStatus `-4`**, which reads like a wrong-stream error and sends you hunting in the wrong place. A Team-ID-pinned `SecCode` check is equally useless — it can't evaluate an external process from inside the extension's sandbox. Apple's own sample and SinkCam both leave the hook an unconditional `return true`; so does macrdp, with the open-injection-target residual documented. (3) **`kCMIOStreamPropertyDirection` is INVERTED from its documented meaning** — measured against our own extension (which registers source-then-sink) the **source reports `direction=1` and the sink `direction=0`**, the opposite of the header's "0 = output / 1 = input". Pick the sink by **stream name** (`kCMIOObjectPropertyName`), because starting the *wrong* stream **returns success** while the extension's sink handlers never fire, so nothing drains the queue and every frame is dropped as "queue full". (4) **macOS never replaces a same-`CFBundleVersion` system extension** — re-activation silently keeps the old one, and a half-swapped state splits the source and sink across two extension processes (the old one keeps serving Photo Booth while the producer feeds the new one) until a reboot; `make-camera-extension.sh` therefore stamps a monotonic build number. **Two debugging aids that make this tractable:** a CMIO extension's `os_log` is **invisible to a normal user** (it runs as the `_cmiodalassistants` role account) — you must `sudo log show --info --debug --predicate 'subsystem == "com.clintcan.macrdp.camera"'`, and without `sudo` you get *nothing*, which looks exactly like "the extension isn't logging"; and since the extension is otherwise opaque, macrdp logs `enqueued`/`dropped_full` every ~90 frames — `dropped_full` climbing with `enqueued` frozen at the queue capacity means **the extension is not draining the sink**. Also budget a **reboot per extension code change** — batch them.
- **`--capture-primary` SILENTLY PREVENTS THE MAC FROM LOCKING — a security caveat, experimentally confirmed 2026-07-20.** While capture-primary blanking is engaged, choosing **Apple menu → Lock Screen** (or ⌃⌘Q) appears to work — no error, no feedback — but **the Mac does not lock**. It stays fully unlocked: anyone with physical access can move the mouse and land in the live session. The blank panel is *gamma trickery, not a lock* (`CGSetDisplayTransferByFormula` to all-black), and it is **not a security boundary** — if macrdp exits, is killed, or crashes, the gamma restores to a live, unlocked desktop. **Cause: `CGDisplayCapture`.** capture-primary takes *exclusive* ownership of every physical display, and `loginwindow` cannot draw its lock screen onto a captured display, so the lock never engages. **Experimentally isolated** (4 tests, ~340 samples, three independent signals — the `CGSSessionScreenIsLocked` session-dictionary key, `ScreenSaverEngine` presence, and macrdp CPU as a capture-liveness proxy): capture ON + caffeinate ON → no lock (170 samples); capture ON + **caffeinate killed** → still no lock (80 samples, so the `caffeinate -dimsu` display assertion is **exonerated** — it was the obvious suspect and is not the cause); capture **OFF** + virtual display still ON → **locks normally** (positive control, lock observed for ~14 s then released). **Scope: this is specific to the capture-based blanking mode — a plain `--virtual-display` session is NOT affected** (the positive control had the vd active and locked fine). `--detach-primary` is untested but plausibly similar, since it also takes over the physical panels. **Practical guidance:** treat a capture-primary Mac as *physically unsecured* — it cannot be locked while a session is engaged. If you need the machine locked, disconnect (the capture releases on last-client disconnect, restoring normal locking) or don't use capture mode. Note that **remote unlock is impossible either way** — macOS blocks synthetic `CGEventPost` input to the login window and secure-input contexts — so even a mode that *showed* the lock screen would not let you type into it. **And when locking DOES work (capture off), the lock screen renders on the PHYSICAL display, not the virtual one** (observed 2026-07-20): the remote RDP user never sees it, and the password must be typed physically at the Mac. So a locked Mac is unreachable remotely by *two* independent mechanisms — the lock screen isn't on the display the client is watching, and macOS blocks synthetic input to the login window even if it were. Any future 'show the lock screen remotely' work would have to solve both, and would still leave a screen you cannot type into. **FIXED 2026-07-20 by a new mode: `--shield-primary` (config `PRIMARY_MODE=shield`) — and the fix is EXPERIMENTALLY CONFIRMED at the mechanism level.** A standalone probe (`shieldprobe.swift`) put opaque black windows at `CGShieldingWindowLevel()` over the panel with **no `CGDisplayCapture` and no gamma write**, and the operator locked the Mac at the keyboard: **11 of 120 one-second samples reported `CGSSessionScreenIsLocked`, with repeated locked→unlocked transitions** (a return to unlocked requires typing into a *visible* password field, which also rules out the "lock engaged invisibly behind the shield" failure mode). Contrast the original experiment: `--capture-primary` never reported locked across ~250 samples. So a shield window does **not** reproduce the bug. **Note what this does and does not settle.** It does *not* isolate whether the original cause was `CGDisplayCapture` or the gamma LUT — the recorded experiment never separated them (they are always installed together; there is no gamma-without-capture arm), so that attribution remains an inference. But it makes the question **moot for this fix**: `--shield-primary` uses *neither* mechanism, so it avoids the cause whichever one it was. The fix is robust to the open question. The implementation is a blanking mechanism that doesn't capture: `ShieldedPrimary` (`src/virtual_display/mod.rs`) keeps the identical arrangement transactions (vd→`(0,0)` as main, physicals aside, `ConfigureForSession` — see `CapturedPrimary` for why ForSession is load-bearing) but hides the panel with an **opaque black window** per physical display, drawn by a new `macrdpshield` helper process (`gui/Sources/macrdpshield`, same architecture as `macrdphud` — helper is the IPC server, macrdp the client, parent-pid watchdog). **It also fixes the ~250 ms re-mode flash** documented in the gamma-blanking note above, for free and for the same reason: a window survives a display reconfiguration, whereas gamma is reset by one and cannot be re-written until the reconfiguration commits. **Trade-off, stated plainly:** capture was also what confined the local pointer, so under a shield someone physically at the Mac can move the pointer and disturb the remote cursor. Their *clicks* are swallowed (the shield takes mouse events) and their *keystrokes* behave exactly as before (capture never blocked the keyboard). For an unattended machine that trade is worth it — a lockable Mac beats a confined pointer — but it is a real trade, which is why this is a **third mode rather than a rewrite of `--capture-primary`**: existing installs keep their exact behaviour until they opt in. **Fail-safe direction, precisely:** a **missing** helper binary aborts *startup* (`spawn_shield_helper` is `?`-propagated in `main.rs`). An **unreachable** helper at engage time is different and weaker — `install` fails, but its caller is the session watcher, whose error arm only `warn!`s, so **the RDP session proceeds with the physical desktop visible and a log line as the sole notice**. Don't read "refuses to start" as covering the runtime path. To make that failure detectable at all, SHOW/HIDE are **acknowledged**: the helper replies with the number of displays it actually covered, and `install` refuses to engage if that is fewer than the physical displays it enumerated. Without the ack a write into a kernel socket buffer returned `Ok` in three distinct situations that all leave the desktop fully visible — a wedged accept loop, a stale helper or squatter holding the port, and a display absent from `NSScreen.screens`. A helper that dies *mid-session* still leaves the panel visible, and note this is **not** the same end state as a SIGKILLed `CapturedPrimary`: there, macrdp died too and the session ended; here macrdp keeps serving. Nothing currently supervises or restarts the helper. **A display attached mid-session IS covered** — SHOW carries an *exclude* list (the vd) rather than an include list, so the helper re-derives "everything else" from `NSScreen.screens` on every screen-layout change; an include list would have been a snapshot that silently missed hotplugs. **RESOLVED 2026-07-20 by keep-physical-main (default). The mode locks AND the lock screen is visible.** The intermediate defect below was real and is now fixed; read it for why the mode is built the way it is.
**THE FIX (live-verified):** `--shield-primary` **no longer moves the vd to `(0,0)` as system main** (default; `MACRDP_SHIELD_KEEP_PHYSICAL_MAIN=0` restores the old behaviour). The physical panel stays main, so `loginwindow` — which draws on the main display — renders the lock screen on the **physical panel, over the black shield, where it is visible**. Live-verified on a real shielded session: ⌃⌘Q → **the password field appeared** and unlocked normally (contrast the vd-as-main run below, where it was invisible). `install` skips the arrangement tx entirely, `Drop` has nothing to restore (`lowered shields (no arrangement was moved)`), and `capture.rs` skips `reanchor_as_main` in this mode so a resize doesn't silently re-promote the vd.
**KNOWN COST, NOW LIVE-MEASURED (second-machine test 2026-07-20):** with the vd not main, the **menu bar + Dock stay on the (shielded/black) physical panel** instead of on the display the client sees — the remote desktop has **no menu bar and no Dock**. Confirmed on a real second-machine RDP client (not loopback — the loopback client window sits *under* the full-screen shield and can't be seen). **Verdict: usable anyway** — windows are reachable and `Ctrl+Alt+G` (the gather-windows hotkey) pulls app windows onto the visible vd, so you work by gathering rather than clicking a Dock. You cannot have the lock visible *and* the Dock on the vd; they are the same `(0,0)`/main bit, so this is an inherent trade, not a fixable bug.
**LOCK vs. the REMOTE SESSION — measured on the same second-machine test, and it's the reassuring result:** while the Mac is locked (physical panel shows the password screen), the remote client **still displays the vd's live desktop** (loginwindow covers only the *main* = physical panel, not the vd), **but the remote session cannot control it** — mouse clicks do nothing and keystrokes do not reach the desktop. That is macOS blocking synthetic `CGEventPost` input to a locked session, exactly as intended: **locking freezes the remote session's desktop access, not just local access.** One curiosity observed: remote *keystrokes* land in the **lock-screen password field** (not the desktop). This is **not an escalation** — to hold the RDP session at all you already authenticated with the account password, and the field renders on the physical panel the remote user cannot see — but it is a surprising behaviour to re-examine if this mode is ever made the default or its input path changes. Minor residual: a person watching the remote client sees the desktop while the Mac is locked (they are already authenticated, so it is the same trust boundary as the session itself), i.e. locking does not *blank* the remote view, it only *freezes* it.
**THE DEFECT THIS REPLACED (vd-as-main, now off by default):** The lock *worked* but **you could not see the lock screen to unlock it, and the physical panel showed the LIVE DESKTOP while the Mac was locked.** Observed on a real shielded session (`--virtual-display --shield-primary` + a connected client): operator pressed ⌃⌘Q → panel went **black → live desktop** (their real desktop, not wallpaper) → **no password field was visible anywhere**; typing produced no visible feedback and they could only get back in with **Touch ID**. The Mac was genuinely locked (Touch ID was required), so this is not "the lock silently no-opped" like `--capture-primary` — it is a *different* failure: **locked, unreadable, and leaking the desktop.**
**Mechanism (best current explanation, not yet isolated):** all three headless modes move the vd to `(0,0)` as **system main**, and `loginwindow` draws the lock UI on the **main** display — which here is the *headless virtual* display, so the password field renders where nobody can see it. Meanwhile the physical panel keeps compositing the user-session desktop. Compounding it, the lock **ended the RDP session** (the local test client died → `SessionTracker::leave` → `ShieldedPrimary::drop`), which **lowered the shield 2 s later and exposed the desktop**. The session-death half may be an artifact of running the client on the same Mac (a remote client would not die), but the invisible-password-field half is **not** — it would persist with a remote client, just over a black shield instead of a bare desktop.
**Why this doesn't simply invert the earlier probe:** `shieldprobe.swift` had **no virtual display**, so the physical panel *was* main and `loginwindow` drew there normally. The vd-as-main variable is exactly what the probe could not test, and it is what breaks. Both results stand; they test different things.
**Security net-assessment vs `--capture-primary`:** still arguably better (the machine actually locks, so a passer-by cannot *use* it) but now with its own leak (they can *read* the screen), and effectively unusable at the keyboard without Touch ID. **Not a clean win, so the mode ships but must not be recommended, and `capture` must not be migrated.** Candidate directions, none implemented: keep the physical panel main while shielding (loses the Dock/menu-bar-on-vd behaviour that makes headless useful), detect the lock and restore the physical as main + keep the shield up, or accept + document Touch-ID-only unlock.
**VERIFICATION STATUS — verified:** that a shield window does not *block* locking (the probe above — `loginwindow` does draw above `CGShieldingWindowLevel` when the physical panel is main), the full engage/lower lifecycle against a real client (connect → `shielded_count=1` + helper ack → `ShieldedPrimary::drop` → restore), frame encoding, end-to-end IPC + ack, the parent-death watchdog, the bind-failure exit, recv-timeout recovery from a wedged peer, and the CLI guards. **REFUTED as a usable security control:** see the live-test block above. **NOT yet verified: the assembled mode end-to-end** — nobody has run `macrdp --shield-primary` with a real RDP client attached and then locked the Mac. The mechanism is proven; the integration is not. Also untested: Mission Control/Exposé (which renders live window thumbnails), native-fullscreen spaces, and display wake. **And `--detach-primary` remains untested for the original lock bug** and is plausibly affected too, since it also takes over the physical panels.

**UPDATE 2026-07-22 — `--shield-primary` now engages on SINGLE-PANEL AUTO-MIRROR hardware (a MacBook with no external display), via a mirror-break + displace; live-verified end-to-end on a real second-machine client.** On such hardware, creating the vd makes macOS **mirror the vd onto the built-in panel**: the panel drops out of `CGGetActiveDisplayList` (online-but-inactive), the mirror set collapses to ONE screen in `NSScreen.screens` (the vd), and the panel is the SAME framebuffer as the vd — three separate reasons the original shield code found "no physical display to shield" and the session proceeded with the desktop **fully visible** (the overlay watcher's error arm only warns). The fix is a three-step engage in `ShieldedPrimary::install`: **(1) fall back to `CGGetOnlineDisplayList`** when the active list is empty (mirroring what Detached/CapturedPrimary already did); **(2) BREAK the vd→physical mirror** (`CGConfigureDisplayMirrorOfDisplay` to `kCGNullDirectDisplay`, `ConfigureForAppOnly` so SIGKILL/crash auto-reverts) so the built-in becomes an independent, shieldable display; **(3) DISPLACE the newly-separate panel to `x = vd_width`** — load-bearing, because after the break both displays sit at identical `(0,0)` bounds, the user's windows stay on the *physical*, and the client watches the *vd*: without the displace the remote "resets to an empty desktop" a few seconds into every connect, and the window-gather can't fix it (with identical bounds, "move onto the vd" is also inside the physical, so macOS keeps the window put). With the vd sole owner of `(0,0)`, macOS re-homes the windows onto the vd on its own; a detached two-sweep gather runs as a safety net once install has fully succeeded. **`Drop` re-mirrors on a clean disconnect** (a `ForAppOnly` break only self-reverts on process EXIT, and macrdp keeps running), and — after a live incident — **both post-mirror-break failure paths (SHOW-ack exhaustion, arrangement-tx failure) also re-mirror** before returning, since they bail before `Self` exists and `Drop` would never run; without that, a failed engage stranded an un-mirrored, displaced, empty panel for the process lifetime. The SHOW ack itself needed **backoff** (300…2000 ms, 7 attempts, ~13 s worst case): right after the mirror-break the helper is relaying out from the screen-change notification *while* macrdp's own gather sweep churns the WindowServer, and a flat 4×300 ms retry exhausted live — and because that failure path calls `hide()`, it took down even the helper's self-raised shields, leaving the desktop visible for the whole session. Two residuals, stated honestly: **(a) the displace makes the vd the system MAIN display, in tension with `MACRDP_SHIELD_KEEP_PHYSICAL_MAIN`'s lock-screen rationale** — no observed regression, because on auto-mirror hardware the vd is *already* main even idle (it is the mirror master), so the physical was never main on this hardware class and lock-while-shielded here is **UNVERIFIED** (test ⌃⌘Q on a live shielded session before relying on it); **(b)** a happy side effect on this hardware: with the vd (e.g. 1728) wider than the panel (1440), the **Dock + menu bar land on the vd** (the largest-online-display heuristic, see the Dock sizing note above), so the remote gets both despite keep-physical-main — the documented "no Dock on the remote" cost does not bite when vd > panel. **UPDATE 2026-07-27 — the OPPOSITE case (vd SMALLER than the panel) also does NOT reproduce the detach/capture-primary "Dock sizes to largest online display" bug (see that note above), on this single-panel auto-mirror path.** Live-measured during a real iOS session where client-resolution auto-adopt shrank the vd to 944×505 against a 1440×900 built-in panel — exactly the trigger condition that bug describes: `CGWindowListCopyWindowInfo` showed the Dock's own window at `x=0 y=0 w=944 h=505`, correctly sized and positioned on the vd, not the panel. Reasoning: that bug's mechanism is "Dock follows the largest ONLINE display"; here Dock instead follows whichever display is **main**, and on this hardware class the mirror-break + displace in step (3) above makes the vd main regardless of its size relative to the panel (residual (a)) — so the size comparison the detach/capture-primary bug depends on never enters into it. Not yet verified on multi-panel/extend hardware, where the vd is never forced to main this way. Multi-panel/extend hardware is untouched (no target mirrors the vd ⇒ every new step no-ops).
**Also addressed 2026-07-20: the `--capture-primary` failure is no longer silent *in the log*.** `CapturedPrimary::install` now emits a `tracing::warn!` on every engage ("SECURITY: while --capture-primary is engaged this Mac CANNOT be locked…") so an operator reading `macrdp.log` learns of it without having to find this note. That is a *disclosure* fix, not a *behaviour* fix — the Mac still cannot lock, and someone standing physically at the machine still gets no feedback when Lock Screen no-ops. The two real candidate fixes remain open: (a) detect a lock attempt and release the capture, or (b) replace gamma blanking with a black shield-window helper process (the same architecture the app-switcher HUD uses — AppKit windows are main-thread-only and tokio owns main), which would also fix the ~250 ms re-mode flash documented in the gamma-blanking note above. (b) was chosen as the preferred design and deliberately deferred.
