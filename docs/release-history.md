# Release history

What each release delivered, newest first. (This is the narrative version —
see the [GitHub releases](https://github.com/clintcan/macrdp/releases) for
tags, dates, and downloadable artifacts.)

## v0.8.27 — the reconnect-blank-cracked release

The mstsc **reconnect-blank is fixed at last** — a client-side EGFX surface-retention bug that had been documented as "not server-fixable" for months (mstsc retains its output surface across an in-process reconnect and composites the stale one → black screen; the only recovery was to fully close and reopen the mstsc window). The breakthrough: on a detected blank, the server sends a bare RDP **core Deactivation–Reactivation** (Server Deactivate All → new Demand Active) that **preserves the EGFX channel and surface** — no surface delete, no channel close, no graphics reset (all of which were exhaustively proven client-fatal in prior attempts). Re-running just the core capability handshake makes mstsc **re-map its retained surface and present again, in place, with no disconnect**. **Live-verified on real mstsc/WiFi: 9/9 blanks healed across two runs, EDR=0 → presenting in ~1-2 s, zero drops.** It's the default recovery action now (a connection drop is only the fallback if the reactivation ever fails to heal). Detection was also sped up with a wall-clock fast-path so a static blank heals in **~4 s** instead of the previous ~70 s. Still RTT-gated and QoE-gated, so FreeRDP and high-latency links are untouched. **`--fork-workers` is no longer needed** for reconnect reliability (and stays a net-negative for interactive mstsc — see v0.8.26 notes); single-process + `--enable-h264` + blank-recovery is the recommended interactive config. Implementation is a zero-vendored-change injection (a no-op `DisplayUpdate::Resize` to the current size reuses the server's existing reactivation path).

## v0.8.26 — the roaming-client release

UDP multitransport now configures and cleans up after itself, so the UDP switches (`--enable-udp-multitransport`, `--enable-lossy-audio`) are **safe to leave permanently enabled on a client that moves between networks**. (1) **RTT-gated offer**: the server measures each connection's TCP round-trip time at accept and simply never offers UDP to links at/above ~80 ms — LAN/WiFi sessions get the loss-resilient UDP audio path, VPN/ZeroTier/mobile sessions run plain TCP from the first byte with no tunnel to wedge. (2) **Tunnel-lifecycle hardening**: an ended session's abandoned tunnel now retires quietly instead of triggering the 10-minute offer cooldown (a false cooldown that silently downgraded healthy-LAN reconnects); a tunnel that wedged *before* its session ended is still correctly adjudicated as dead so the reset-cycle protection can't be evaded; offer cookies are evicted on every connection end (previously leaked one registry entry per failed handshake, with a zombie-peer window); and all three peer-removal paths lower the shared tunnel flag so audio can never route into a nonexistent tunnel. (3) **`--fork-workers` parity**: workers sample the link RTT themselves, so the link-aware features (blank-recovery gate, bitrate seeding) apply under the per-connection-process model too. 

## v0.8.25 — the resilient-link release

three session-killers fixed, all live-verified over ZeroTier (including over a mobile connection). (1) **Oversized-cursor fix**: macOS "shake to locate" (or any enlarged pointer) at Retina backing pixels overflowed the RDP pointer PDU's 64 KB mask limit, and the encode error tore down the whole session — the sprite is now downscaled to fit, aspect- and hotspot-exact. (2) **Link-aware blank recovery**: the server samples the kernel's TCP RTT for every connection at accept; on fast links the mstsc reconnect-blank auto-heal works exactly as before, on slow links the evidence window scales with RTT, and past ~80 ms the force-drop is withheld — on high-latency links a *rendering* client reports zero render-time, so the old detector dropped working sessions every ~5 s and the repeated drops caused the very blank it exists to fix. (3) **RTT-seeded adaptive bitrate**: slow links start at ceiling/3 (6 → 2 Mbit) and climb as headroom allows, instead of overshooting a distant pipe for the first seconds. (4) **UDP tunnel-death detection**: a wedged multitransport tunnel now falls audio back to TCP within ~30 s and suppresses further UDP offers for a cooldown, so mstsc's ~60 s dead-tunnel reset reconnects as a stable plain-TCP session instead of cycling. 

## v0.8.24 — the remote-link release

(1) **RTT-aware rate control**: the `--adaptive-bitrate` controller now measures **standing queue delay** (each frame's ship→ack round trip minus the link's windowed-minimum RTT) instead of a frame count that conflated latency with congestion — a clean-but-distant link (VPN/ZeroTier at 200+ ms) keeps **full quality** instead of crater-climbing to 10 fps, a genuinely thin pipe degrades gracefully and converges to alive-and-in-sync (lab: standing queue drained 2.9 s → 45 ms on a saturated 500 Kbit link), and a **no-ack distress fallback** keeps the controller live even when a fully choked client stops acking entirely; IDR backoff now covers both transports. Verified on a real ZeroTier link. (2) **Windows App for Android support**: that client advertises EGFX with AVC disabled, and confirming-then-ignoring the pipeline was a protocol violation it hard-disconnected on ~2 s in — macrdp now declines the graphics pipeline at the channel level and serves legacy updates; verified on a real device. (3) **Blank recovery heals ~2× faster** (drop-first + a reconnect-storm guard; live-verified). (4) **A quieter server**: idle pollers park (0.0% CPU with no client), and per-mouse-move / per-frame WindowServer round-trips are throttled. Caveat shipped with it: `--enable-lossy-audio` is **LAN/WiFi-only** for now — over ZeroTier-class overlays its UDP tunnel can wedge and mstsc's ~60 s dead-tunnel timeout resets the session cyclically (fixed in v0.8.25 by tunnel-death detection; on main the offer is now also RTT-gated, so the switch is safe to leave on). 

## v0.8.23 — health-check watchdog

`launchd`'s `KeepAlive` only restarts macrdp on an outright *crash*; a process that's alive but **wedged** (a deadlocked async runtime, every worker thread blocked) would otherwise stay up and unreachable with nothing to revive it. The watchdog probes the runtime from a dedicated OS thread (which keeps ticking even when the runtime is stuck) and, on a sustained wedge, exits with a distinct code so `launchd` — or the `--fork-workers` supervisor — restarts a fresh process. Conservative by default (a wedge must persist ~90 s before a bounce, so load spikes never trip it), on when running headless under launchd, and env-tunable (`MACRDP_HEALTHCHECK*`); it closes the last reliability gap `KeepAlive` couldn't. 

## v0.8.22 — automatic mstsc reconnect-blank recovery

A reconnecting `mstsc` that lands on its own stale retained surface (decodes every frame but never composites — the long-standing "black screen on reconnect with `--enable-h264`") is now **auto-detected and healed with no user action**. Detection reads the client's own QoE Frame Acknowledge `TimeDiffEDR` (decode+render time): a blank session reports it as zero on every frame while a rendering one shows nonzero within ~200 ms — a signal proven by decrypted-pcap comparison and verified live. On detection the server drops the connection (straight away by default — the non-destructive fresh-surface remap was verified never to heal `mstsc` and is now opt-in via `MACRDP_BLANK_RECOVERY_MAX_ATTEMPTS`); a **Server Auto-Reconnect Cookie** (MS-RDPBCGR ARC) then makes `mstsc` reconnect *itself* and the fresh connection renders, with a consecutive-drop cap so a truly-stuck client gets clear guidance instead of a reconnect loop. Default on (`MACRDP_BLANK_RECOVERY=0` / `MACRDP_AUTO_RECONNECT=0` to disable); pairs with `--fork-workers`. 

## v0.8.15–v0.8.21 — the congestion-responsive rate-control arc

under packet loss an H.264 session now degrades gracefully instead of freezing. **`--adaptive-bitrate`** runs an AIMD controller (standing queue delay — ship→ack RTT minus the windowed-minimum link RTT, EWMA-smoothed — + hysteresis + a 3-zone hold) on **both** the UDP tunnel and the TCP path, so `--bitrate` is a ceiling that backs off under congestion; once it bottoms out, a **frame-rate floor** sheds fps (never to zero) so video stays choppy-but-steady-and-in-sync rather than freezing. An **EGFX-over-UDP watchdog** auto-de-migrates a wedged reliable UDP tunnel back to TCP (incl. proactively on minimize/restore). And **`--enable-lossy-audio`** streams RDPSND over a lossy UDP/DTLS tunnel with 1+1 redundancy (each datagram sent twice → p→p² loss) — soak-verified smooth on real mstsc at 5/10/15% loss where single-send glitches. All verified on real mstsc; every switch is opt-in, default (TCP) behavior unchanged.
