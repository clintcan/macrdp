## v0.10.4 — true-colour cursors, native-style app switching, reverse scroll

Cursor, input and hardening fixes, plus one new option. By default, coloured cursors, the app switcher and the pre-login timeout behave differently; `--reverse-scroll` is off unless you turn it on.

- **Coloured cursors show their true colours, and the pointer hides when an app hides it (#219, thanks @SferaDev).**
  - **Colours:** the wait cursor and other coloured cursors showed red and blue swapped. They are now sent in the byte and row order RDP specifies (`xor_mask_32bpp`: B,G,R,A, bottom row first).
  - **Hiding:** in full-screen video, the pointer now disappears on the client when the video hides it, instead of staying on screen (`fully_transparent` → `DisplayUpdate::HidePointer`). A cursor hidden with `NSCursor.hide()` (rather than replaced by a transparent one) still can't be detected.
  - **Behind it (#255):** our copy of IronRDP never sent a "hide pointer" or "default pointer" update, because an update with no payload produced no bytes. This takes the fix IronRDP made upstream (Devolutions/IronRDP#2274) as vendored divergence (31) in `UpdateFragmenter::encode_next`, to drop at the next pin bump.
- **Alt+Tab and Cmd+\` behave like the native macOS switchers (#197, thanks @antonmos).**
  - A quick Alt+Tab returns to the app you were last in, even after switching by clicking a window or a Dock icon. Apps you only cycled through no longer jump ahead of it (only the landed app is promoted, in `commit_cycle_session`; switches made outside the switcher feed `SWITCHER_FRONT`).
  - Cmd+\` cycles the right app's windows and visits every one, instead of bouncing between the top two.
  - Every plain left click now runs one Accessibility hit-test, on its own `click-focus-hittest` thread, not only under `--map-ctrl-to-cmd`.
- **New option: reverse the mouse-wheel direction (#254, #240).** `--reverse-scroll` (config `REVERSE_SCROLL=1`, or the toggle under Mouse in the menu-bar controller's Input tab) flips the wheel on both axes. It's for a Mac with natural scrolling on, where a tool such as LinearMouse can't see the scroll events macrdp posts. The flip is applied before the wheel accumulator (`wheel_delta`).
- **A client that goes silent before logging in is dropped after 60 s (#256, #186).** Before, a connection that sent its first request and then nothing held the serving connection forever. The 60 s budget leaves room for a client that asks for the password during login. Vendored divergence (32), `SERVE_NEGOTIATION_TIMEOUT`; a timeout returns `TimedOut`, like upstream's `FINALIZE_TIMEOUT`.

**Verified before release**

- CI green on Linux and macOS. `cargo fmt --check` passes on stable and nightly, `cargo clippy --all-targets -- -D warnings` passes, and all 352 tests pass. The new tests were mutation-checked.
- Live on a Mac mini running this exact `main`, with Windows 11 mstsc and Windows App for macOS: connect, reconnect, Option+Tab, and a test window of custom coloured cursors (colours, orientation, and hiding).
- Each change was also tested live on its own:
  - **Cursors:** FreeRDP's log shows the hidden pointer arriving; on both FreeRDP and Windows App the pointer disappears in full-screen YouTube.
  - **Switcher:** cycle order, switching by click and by Dock icon, and Cmd+\` window cycling.
  - **Reverse scroll:** both directions.
  - **Pre-login timeout:** a client that sends a Connection Request and then nothing is dropped at 60.1 s. Measured live, mstsc and Windows App close their own connection 8–21 s into a certificate warning and reconnect after the click, so the budget doesn't cut off a person answering one.
- **Not soaked:** the mini has run this exact code for about half an hour.

**Known issues** (none are new in this release)

- An mstsc window that has reconnected several times decodes video more slowly above ~2 Mbit/s, so `--adaptive-bitrate` can still briefly dip there. Closing and reopening mstsc avoids it.
- With mstsc, the UDP tunnel goes quiet about 90 s into a session, and the session continues over TCP.
- Windows 10 mstsc shows a black screen or starts an H.264 session frozen (#226, #229). Fixes are in review (#228, #230).

## v0.10.3 — Finder writes to redirected drives, and the keyframe backoff works

A bug-fix release. By default, only drive redirection behaves differently; the keyframe change also applies to every H.264 session, but keeps the same cadence.

- **Finder can write to a redirected drive (#253).**
  - **The bug:** the drive's files and folders were reported as owned by "system", with read-only access for everyone else. Finder therefore treated the drive as read-only: New Folder silently did nothing, and a rename failed with "another operation is in progress". Commands in Terminal still worked, which is how this went unnoticed.
  - **The fix:** files and folders are now reported as owned by the user macrdp runs as (the server process's uid/gid in the node attributes).
- **Renaming a file or folder on a redirected drive keeps its identity (#253).** A rename used to give the item a new identity on our side, while Finder kept using the old one. The visible effect was an error logged every 5 seconds for as long as the Finder window stayed open; files inside a renamed folder could still be looked for at the folder's old location. A renamed item now keeps its identity, and the paths of everything inside a renamed folder move with it (`FsCache::rename`).
- **`--adaptive-bitrate`'s keyframe backoff now takes effect (#252).**
  - **The bug:** under congestion, the backoff is meant to hold back the periodic keyframe, but VideoToolbox ignores a keyframe-interval change made after encoding starts. So the backoff never did anything.
  - **The fix:** the encoder now schedules the periodic keyframe itself (`keyframe_due`; VideoToolbox gets a never-firing `VT_KEYFRAME_BACKSTOP`).
  - **The cap:** with the backoff working, a session that stays congested would get no healing keyframe at all, so the held-back interval is capped at about 10 s of frames (`stretched_keyframe_interval`; about a minute under the 10 fps floor).

**Verified before release**

- CI green on Linux and macOS. `cargo fmt --check` passes on stable and nightly, `cargo clippy --all-targets -- -D warnings` passes, and all 339 tests pass. The new tests were mutation-checked, including one on a real VideoToolbox session.
- **Drive redirection:** live on a Mac mini with FreeRDP redirecting a folder.
  - Before the fix, Finder refused New Folder and rename without sending a request.
  - With only the ownership fix, a rename produced the error every 5 s.
  - With both fixes, creating a folder and renaming a file and a folder produced no errors.
- **Keyframes:** live with mstsc on Windows 11.
  - With adaptive bitrate off, 37 keyframes went out, exactly 120 frames apart: the normal 2 s cadence, now from our scheduler.
  - With adaptive bitrate on in a congested session, keyframes came every 600 frames instead of stopping.
- **Not soaked:** the mini has run this exact code for about half an hour.

**Known issues** (none are new in this release)

## v0.10.2 — clipboard and drive redirection fixes

A bug-fix release: the session no longer freezes when the Mac's clipboard holds something copied on another Apple device, and restarting macrdp with a redirected drive no longer leaves a stuck mount behind. By default, only clipboard sync and drive redirection behave differently.

- **No more session freezes from Universal Clipboard (Handoff) (#198, @antonmos).** When the Mac's clipboard held an item copied on an iPhone or another Mac, a paste on the RDP client made macrdp read it, and macOS then fetched it from the other device over Bluetooth while the whole session waited. That took 70–662 ms in testing, and 17–21 s on the Mac mini on 11-10. macrdp now neither offers nor reads such items (`is_remote_clipboard`), and macrdp's own clipboard writes stay on the Mac instead of being handed to Handoff. On connect, something copied on the Mac while no client was connected now wins over the client's clipboard; otherwise the client's clipboard is used, as before (`skip_connect_time_fetch`, with `session_end_cc` stamped only by a connection that served a client). A lost fetch reply now holds up later copies for at most 60 s (`STALE_REPLY_GRACE`).
  - Trade-off: an item copied on a third Apple device isn't relayed to the RDP client until something is copied again.
- **A failed connection attempt can no longer break the live session's file paste (#245, @antonmos).** Clipboard state is created for every connection attempt, before authentication. When an attempt failed or lost a preemption, its cleanup could delete the live session's in-progress Windows→Mac paste files. Only a connection that actually served a client cleans up now (its `on_ready` fired).
- **Restarting macrdp with a drive redirected no longer leaves a stuck mount (#251).** A restart could leave the drive's NFS mount pointing at the stopped server. The next start then hung on it until "Disconnect All" was clicked in macOS's "Server connections interrupted" dialog. Now:
  - the mount is made with `deadtimeout=60`, so macOS removes it by itself about a minute after its server disappears, whether from a restart, a crash or a freeze;
  - startup cleanup finds leftover mounts in the kernel's mount table (`getfsstat` with `MNT_NOWAIT`) without touching them, so it can't hang, and each `umount` is bounded at 10 s;
  - a failed unmount is logged at warn with its error.
- Two clarifying comments in `auth_guard.rs` (#242, @SferaDev).

**Verified before release**

- CI green on Linux and macOS. `cargo fmt --check` passes on stable and nightly, `cargo clippy --all-targets -- -D warnings` passes, and all 333 tests pass. The new tests were mutation-checked: breaking each fix fails its test.
- **Clipboard:** live on a Mac mini with Handoff on, copying on an iPhone and pasting on a Windows 11 PC. v0.10.1 froze the session for 70 ms, and for 662 ms with the phone locked. This release refused the request in about 2 ms with no freeze, and normal copy and paste in both directions still worked.
- **Drive redirection:** live on the Mac mini with FreeRDP redirecting a folder.

  | Case | Result |
  |---|---|
  | Restart with the drive mounted | unmounted in 51 ms |
  | Process killed (SIGKILL) | the next start cleaned up the mount in under a second, with no hang |
  | Process frozen (SIGSTOP) | macOS removed the mount by itself after 80 s, and the session survived |
- **#245** is a bug found by reading the code. It wasn't reproduced with a real client.
- **Not soaked:** the mini has run this code for a few hours.

**Known issues** (none are new in this release)

- An mstsc window that has reconnected several times decodes video more slowly above ~2 Mbit/s, so `--adaptive-bitrate` can still briefly dip there. Closing and reopening mstsc avoids it.
- `--adaptive-bitrate`'s keyframe backoff has no effect: periodic keyframes keep their normal interval under congestion.
- With mstsc, the UDP tunnel goes quiet about 90 s into a session, and the session continues over TCP.

## v0.10.1 — mstsc reconnect and video fixes

A bug-fix release for mstsc users: no more dropped sessions after a successful blank-screen recovery, and no more video stutter with `--adaptive-bitrate` on a LAN. By default, only blank recovery (on by default) and the resync hotkey behave differently; the adaptive-bitrate changes apply only when `--adaptive-bitrate` is on.

- **A session that recovered from a blank screen is no longer dropped (#248).** Right after a reconnect, the server can repaint a blank mstsc window in place. Once it has, a single "nothing presented" report from mstsc used to drop the session anyway, so you saw black, then the desktop, then a reconnect dialog. On a static desktop the menu-bar clock tick could cause that once a minute in a loop. After a recovery, a drop now needs a burst of such reports (3 within 10 s) that also make up at least half of the reports since the recovery, and none once the session has shown 5 seconds of picture. Every logged false drop fails at least one of those tests; every logged real blank passes all three. Tunable with `MACRDP_BLANK_RECOVERY_POST_ATTEMPT_ZEROS` and `MACRDP_BLANK_RECOVERY_POST_ATTEMPT_WINDOW_MS`, also settable in `config.env`. (In `should_blank_recover`: the one-zero wall-clock fast path is connect-phase only, the heal-confirmation deadline fires only on QoE silence, and the new zero-burst arm is withheld once established and needs a zero majority.)
- **`--adaptive-bitrate` no longer makes mstsc video stutter on a LAN (#249).** It read mstsc's ~120 ms of decode depth during 1080p60 video as network congestion, though the TCP send queue was empty, and swung between 3 and 0.5 Mbit/s and a 10 fps cap every 3–5 s. Delay now counts as congestion only while it keeps growing, or above 400 ms. Cuts are spaced at least 1 s apart so each takes effect, and the climb back slows near the bitrate where trouble began. Tunable with `MACRDP_ADAPTIVE_QUEUE_RISE_MS` and `MACRDP_ADAPTIVE_QUEUE_CEILING_MS`. (`delay_trend`/`delay_pressure`, `hold_trend_decrease`, `increase_step`/`note_decrease`.) In a closed-loop simulation of the controller: the mstsc LAN model averages 2.89 Mbit/s with no floor intervals (0.85 Mbit/s and 48 before); thin 1.0/1.5/2.5 Mbit/s links average 0.99/1.48/2.49 Mbit/s (0.82/1.15/2.03 before) at the same peak delay; a saturated 500 Kbit link backs off exactly as before.
- **The A/V resync hotkey clears queued video first (#249).** Ctrl+Alt+Shift+R now holds new video until mstsc's decoder has caught up, at most 2 s, before the fresh keyframe, which is what minimize→restore did (`resync_drain_step`).
- A clipboard test that could fail on a slow CI runner now runs on a simulated clock (#250).

**Verified before release**

- CI green on Linux and macOS. `cargo fmt --check` passes on stable and nightly, `cargo clippy --all-targets -- -D warnings` passes, and all 314 tests pass. The new tests replay the logged false-drop and real-blank windows and the measured delay traces, and each part of both fixes is mutation-checked.
- Live with mstsc (Windows 11) on a Mac mini over Ethernet, with YouTube playing, across four rounds. Final round: 7 connections, 3 blank reconnects all healed in place, 0 drops. Adaptive bitrate: 0–12 cuts per connection and no 10 fps periods on a freshly opened mstsc, against 119 cuts and 252 capped frames in one reconnected connection on an earlier build.
- Not soaked: the mini has run this code for about half an hour. v0.10.0's 48-hour soak covered everything else.
- Not tested live: VPN and ZeroTier links with `--adaptive-bitrate`, and Windows App for macOS. Both rest on the replayed logs and models.

**Known issues** (none are new in this release)

- An mstsc window that has reconnected several times decodes video more slowly above ~2 Mbit/s, so `--adaptive-bitrate` can still briefly dip there. Closing and reopening mstsc avoids it.
- `--adaptive-bitrate`'s keyframe backoff has no effect: periodic keyframes keep their normal interval under congestion.
- With mstsc, the UDP tunnel goes quiet about 90 s into a session, and the session continues over TCP.
- Restarting macrdp while a drive is redirected can leave a stale mount until macOS offers "Disconnect All".
- Reading a Universal Clipboard (Handoff) item can stall the session for many seconds; turning off Handoff on the Mac avoids it.

## v0.10.0 — IronRDP update + fixes since v0.9.11

An update to IronRDP plus about four weeks of fixes from contributors. Most of the runtime is unchanged; the behaviour changes are listed below.

**IronRDP update (#194).** macrdp now builds on IronRDP `e258f6a0`, up from `a5d1c682` (391 upstream commits). Several things macrdp used to patch locally are now upstream, so the vendored forks shrank: SuppressOutput, NSCodec, adopting the client's resolution, the keyboard-layout cell, the auto-reconnect cookie, mouse position before button, and auth-gated preemption. macrdp sets them through the builder, including `ConnectionPolicy::Preempt` (upstream's default, `Queue`, would bring back the second-client hang). What it changes for users:

- **A client that stalls while connecting no longer holds the session.** IronRDP now gives the connection's finalize step 30 s (upstream #1890). Before, a wedged client could keep the session slot until another client connected. This replaces #182 (@antonmos).
- **The cursor shows in the iOS Windows App (#211).** 32-bit cursors now carry an AND mask (a backport of upstream #2108, vendored server divergence 29). Reported and confirmed fixed by @JeffSteinbok, who also checked touch mode.
- **FreeRDP and Thincast now get mute-on-minimize.** IronRDP now tells clients the server supports SuppressOutput, so these clients send it, and macrdp mutes the audio and pauses the video while they're minimized, as it already did for mstsc.
- **The auto-reconnect cookie is verified and rotated.** IronRDP now checks a returning cookie and changes it hourly and on every reactivation. A client that reconnects after macrdp restarts carries a cookie that no longer checks out. Upstream refuses that connection, which in testing locked FreeRDP out through repeated retries; macrdp falls back to a normal logon instead, as MS-RDPBCGR 3.3.5.3.11 asks (vendored server divergence 30, reported upstream as Devolutions/IronRDP#2280).

**Fixes and features since v0.9.11**

- `--password-file` reads the password from a file you own with mode 600 or 400 (@rophy, #212).

## v0.9.11 — input fixes

A bug-fix release for mouse and keyboard input, both contributed by @antonmos. The default runtime path changes only in that clicks, drags and scrolls now carry the modifiers you're holding.

- **Held modifiers reach mouse events (#183).** Clicks, drags and scrolls previously carried no modifiers at all, so a Shift-click selection, a Cmd-click or a Shift-drag didn't work as expected. They now carry the keys actually held, whether or not `--map-ctrl-to-cmd` is on.
- **Ctrl+click → Cmd+click under `--map-ctrl-to-cmd` (#183).** A Windows-style Ctrl+click on a link opens it in a new tab instead of a secondary click. Left button only; it's decided once at button-down and kept for the drag and release, and right/middle clicks and scrolling keep the real modifiers (so Ctrl+scroll is still macOS zoom).
- **No stuck buttons or modifiers after a reconnect (#183).** A connection that dropped mid-click left the button held, so every move on the next connection was a phantom drag until the next click. Each newly served connection now releases held buttons and modifiers once — not on a live resize or blank-recovery reactivation (vendored server divergence 24). Held modifiers are also cleared after 10 s with no input (`MACRDP_MODS_RESYNC_IDLE_MS`, 0 disables), so a key-up lost when the client lost focus can't turn every click into a secondary click. Caveat: a drag interrupted by a disconnect completes as a drop at the last cursor position — see `docs/known-quirks.md`.
- **Ctrl+, → Cmd+, under `--map-ctrl-to-cmd` (#184)**, so Ctrl+, opens an app's Preferences.

## v0.9.10 — microphone redirection

A feature release: **the client's microphone presents as a real macOS input device.** Opt-in and EXPERIMENTAL; the default runtime path is unchanged.

- **New: microphone redirection (#191).** `--enable-microphone-redirection` (config `ENABLE_MICROPHONE_REDIRECTION=1`, or the GUI controller's Settings → Redirection → Microphone) negotiates MS-RDPEAI on the `AUDIO_INPUT` channel and feeds the client's mic into **"macrdp Microphone"**, a Core Audio device in System Settings → Sound → Input, Zoom, Teams, FaceTime and QuickTime. The client opts in too (mstsc: Remote audio → Settings → *Record from this computer*). The driver ships inside `macrdp.app` and is installed once from the controller (one admin prompt, Core Audio restarts; no entitlement).
- **Transport:** received PCM goes through a POSIX shared-memory ring into the plug-in inside `coreaudiod`. The ring is created only once the client negotiates the mic, exclusively, at mode 0644, and wiped and removed when the session ends; the plug-in reads it read-only and validates the header. **Other local accounts on the Mac can read a live stream** — see the loopback-IPC note (channel 5) in `docs/macos-gotchas.md`.
- **Format:** 16-bit PCM at 44.1 kHz only (there is no resampler). A client that can't offer it gets no mic, and macrdp logs why.
- **Upstream:** the protocol layer is vendored `ironrdp-server` divergence (25). Upstream IronRDP now has `ironrdp-rdpeai` (#1645, #1946); macrdp adopts it at the next pin bump.
- **Verified:** live on Windows 11 mstsc with the entitled build — the ring-v2 test recorded the client's voice at −10.6 dB peak; on the final build the log confirms the 44.1 kHz format, a minute of streaming and a clean release on disconnect. Not live-tested on FreeRDP's `/microphone`.
- **Fix (#190):** `--lock-on-disconnect` no longer locks underneath a client that reconnected but is still handshaking (~10 s over ZeroTier). A pending lock holds for a recent authenticated reconnect, or briefly for a just-accepted connection, capped at 30 s so an unauthenticated peer can only delay it.

## v0.9.9 — rich-text clipboard, both directions

A feature release: **formatted text now survives the clipboard in both directions.** On by default; `--no-rich-clipboard` (config `RICH_CLIPBOARD=0`) restores text + images only. **File copy/paste is unchanged.**

- **New: rich text (#189).** The Windows `HTML Format` and `Rich Text Format` clipboard formats map to the Mac's `public.html` and `public.rtf`, so bold, colours, lists and links cross between Word, Outlook or a browser and Mail, Notes, TextEdit or Pages. A Windows copy is fetched as every representation macrdp can use — plain text, one rich format (HTML preferred, RTF otherwise), one image — and published as a **single** pasteboard item, so the app you paste into picks the richest type it understands: a Chrome "Copy Image" (bitmap *plus* HTML) still pastes as an image. A copy offering files always takes the file path. Images embedded *inside* rich text generally don't survive (Word's HTML points at local temp files).
- **Fix: Windows-copied text and images no longer echo back.** They weren't marked as macrdp's own pasteboard writes, so the poller advertised them straight back to Windows, which made the client take over its own clipboard with only what was fetched. Marked now — in a separate marker from the file-paste one, so disconnect cleanup never wipes copied text.
- **Live-verified on Windows 11 (build 26100) mstsc over ZeroTier**, 8/8: Word → TextEdit, Firefox/Chrome → Notes (links clickable), TextEdit → Word, Chrome Copy Image → Preview, files both ways, a Word copy pasted back into Word, plain text into Notepad/Terminal, and `RICH_CLIPBOARD=0`. The live test found and fixed three bugs:
  - **Firefox and Word announce each copy twice**, 5–180 ms apart. Restarting the fetch at once let the first announce's reply be attributed to the second fetch's request — text in the HTML slot and vice versa — so the copy arrived as plain text. The new copy's first request now waits for the superseded reply and discards it (bounded by a 5 s grace).
  - A transient format error on a re-announce: a failed representation is now retried once.
  - **A trailing `^@` pasting Word text into Terminal.** Word can send several trailing NULs and only one was stripped — pre-existing since the first text-clipboard commit. Text now ends at its first NUL.
- **Tip:** if a paste into Word keeps bold but loses colour, that's Word's *Merge Formatting* paste mode, not macrdp — choose *Keep Source Formatting*.

Pre-tag gates: `cargo fmt --check` clean on stable and nightly, `cargo clippy --all-targets -- -D warnings` clean, 239 tests passing.

## v0.9.8 — lock while away: `--lock-on-disconnect` + `--auto-unlock`

A feature release for headless, remote-only Macs, plus a real `--shield-primary` bug fix. **Everything new is opt-in; the default runtime path is unchanged.**

- **New (experimental): `--lock-on-disconnect` (#181, @antonmos).** Locks the Mac about 25 s after the last RDP client leaves (config `LOCK_ON_DISCONNECT=1`). It needs one of the headless modes (`--detach-primary` / `--capture-primary` / `--shield-primary`). The delay is a cancellable safety buffer, so a blank-recovery self-heal reconnect (up to ~12–15 s) doesn't lock under a session that's coming back; tune it with `LOCK_ON_DISCONNECT_DELAY_MS`. It locks by starting the screen saver — the old `CGSession -suspend` trick no longer exists on macOS 26 — which is only a real password-required lock when *Require password after screen saver begins* is **Immediately**; macrdp warns at startup when it isn't.
- **New (experimental): `--auto-unlock` (#181, @antonmos).** When a client connects while the Mac is locked, macrdp types the account password into the lock screen (config `AUTO_UNLOCK=1`) — the same password PAM validated at startup and the connecting client proved via CredSSP. **Off by default** because it acts on the *physical* machine: once it fires, anyone at the Mac has a live desktop, and it undoes a lock it didn't set. Safety properties: a shared per-lock budget of **2** real password submissions (below macOS's 3-free-attempt throttle), reset only on a *confirmed* unlock; it skips rather than guesses when Caps Lock is on, the active layout can't type a character, or the lock state can't be read; and every character is resolved to a keystroke before any is typed. Skipped under `--skip-auth`.
- **Live-verified on a Mac mini** (M1, macOS 26.5): the final pass ran 4/4 lock/unlock cycles over the LAN, lock ~22.5 s after disconnect, unlock ~3 s after connect. The earlier passes — run over ZeroTier from another island, with nobody at the machine — found two bugs — a too-short detection window that raised false "gave up" alarms, and a false give-up leaving the budget spent so the *next* lock couldn't be undone remotely — both fixed and re-verified before merge.
- **GUI (#188).** The menu-bar controller's Display tab gains a **Lock while away** section with both toggles — disabled and cleared unless a Detach/Blank mode is picked, and with a warning when the lock is on without auto-unlock, since a remote-only Mac is unreachable once it locks.
- **Fix: `--shield-primary` now engages on a lid-closed MacBook (#187, @antonmos).** A closed lid removes the built-in panel from the display list entirely, so `ShieldedPrimary::install` failed with *no physical display to shield*. Because the overlay watcher only warns, that silently disabled the shield, `--restore-windows-on-disconnect` **and** the connect-time window gather at once, while the RDP session itself kept working. It now degrades to an empty shield.
- **Known issue:** with `--lock-on-disconnect`, a reconnect started roughly 12–22 s after leaving can be locked mid-handshake — a connection only counts as "back" once it's fully connected. With `--auto-unlock` it self-corrects in about 3 s; with the lock alone, a remote user lands on a lock screen they can't get past. Tracked as a follow-up.
- **Repo hardening (no runtime change):** `.github/CODEOWNERS` with required code-owner review on `main`, fork-PR CI runs gated on approval for all outside collaborators, and SHA pinning of actions enforced.

Pre-tag gates: `cargo fmt --check` clean on stable and nightly, `cargo clippy --all-targets -- -D warnings` clean, 212 tests passing.

## v0.9.7 — dependency & security patch: rustls, cryptoki, h2

A patch over v0.9.6 that carries **three security advisories** out of the dependency tree, plus one user-visible UI change. **No change to the default runtime path** beyond the dependency updates themselves.

- **Security: `rustls` 0.23.40 → 0.23.45 (RUSTSEC-2026-0285).** Rustls accepted TLS 1.3 handshake messages sent at the wrong encryption level — for example a plaintext `EncryptedExtensions` packed into the same record as the `ServerHello` — where RFC 8446 §5.1 requires terminating with an `unexpected_message` alert. The handshake transcript is still authenticated, so a network-position attacker **cannot** alter or complete a handshake; the practical effect is that a peer could send in plaintext what should have been encrypted without rustls rejecting the connection. This is macrdp's own TLS stack (every client connection terminates here), which is why it's the headline of this release. Functionally the same bug as Go's CVE-2025-61730.
- **Security: `cryptoki` 0.12.0 → 0.12.1 (RUSTSEC-2026-0286).** `cryptoki` treated the `CKA_ALLOWED_MECHANISMS` `ulValueLen` **byte** count as a `CK_MECHANISM_TYPE` **element** count, so a valid non-empty attribute returned through the safe `Session::get_attributes` API could construct an out-of-bounds slice — a crash, or disclosure of adjacent heap words. Reaches macrdp transitively through `sspi` → `ironrdp-connector`.
- **Security: `h2` 0.4.14 → 0.4.16 (RUSTSEC-2026-0258).**
- **Housekeeping: `chacha20` 0.10.1 → 0.10.2.** 0.10.0 and 0.10.1 were **yanked** — not for a vulnerability, but for a correctness bug (an SSE4.1 intrinsic used in the SSE2 backend of the RNG and legacy 64-bit-counter variants, RustCrypto/stream-ciphers#580). The failure mode is an illegal instruction on an x86 CPU with SSE2 but without SSE4.1, so macrdp's exposure was nil — Apple Silicon never compiles those backends and every Intel Mac has SSE4.1 — but a yanked crate in the lockfile is a supply-chain signal worth clearing.
- **Consequential updates** pulled in by the rustls bump, all in the crypto provider beneath it: `aws-lc-rs` 1.16.3 → 1.18.1, `aws-lc-sys` 0.40.0 → 0.45.0, `rustls-webpki` 0.103.13 → 0.103.15.
- **The app-switcher HUD now looks like the native Cmd+Tab switcher (#185, @antonmos).** The `--app-switcher-hud` overlay — the switcher macrdp draws so the RDP client can see it — moves from its first-cut "spike" look to the system style: a light translucent slab (`.popover` material forced vibrant-light, continuous 28 px corner, hairline border), bigger icons that scale to fit the display (144 px for a few apps, shrinking to stay within ~80 % of the display width, floored at 32 px), and a subtler selected-icon ring. Opt-in as before; nothing changes unless `--app-switcher-hud` is passed.

Each dependency fix was verified against the CI-pinned `cargo-deny` on both invocations the workflow runs (the root tree and the standalone vendored `ironrdp-rdpeudp` lock), and the daily scheduled scan is green again after being red 2026-09-15 → 09-17.

## v0.9.6 — bug-fix patch: scroll-down regression + an unauthenticated accept-loop DoS

A bug-fix patch over v0.9.5, both fixes from @antonmos. It corrects **two things that shipped broken**: a scroll regression introduced by the v0.9.5 pin bump, and an unauthenticated remote DoS in the second-client-preemption path latent since v0.9.3.

- **Fix (regression): scroll-down is no longer inflated ~255× (#179).** v0.9.5's pin bump moved `ironrdp-pdu` past its *own* wheel-rotation decode fix (it now decodes the 9-bit `WheelRotationMask` as proper two's complement), but did not delete the vendored compensation (divergence 17) that existed only to correct the *old* buggy decode — so the compensation started **double-correcting**: a gentle downward tick (−1) became −255, a max-speed scroll, on every downward gesture, while upward scrolling (positive, untouched) stayed correct. That asymmetry — down runs away, up is fine — is the fingerprint (macrdp issue #113, reappearing in the opposite direction). Worst on the macOS Windows App's fine-grained ±1..±3 trackpad deltas; mstsc's whole ±120 notches were ~13 % too fast. Divergence 17 is **retired** (the delta now passes through unchanged), and a new **end-to-end round-trip test** (encode → decode → `MouseEvent`, both directions) pins the contract so a future pin bump that changes the decode fails in CI, not in a user's hands.
- **Fix (security): an unauthenticated remote client can no longer wedge the accept loop (#180).** The second-client-preemption path (added v0.9.3) awaited a candidate's negotiation **unbounded** — and that negotiation blocks on socket reads from a peer that has not yet authenticated. A single TCP connection that completed the handshake and then **sent nothing** parked the accept loop: accepts were already gated off for the rest of the session, and once the live session ended the loop blocked on the handoff await with no `select!` left — no accepts, no event drain, not even a `Quit`. One silent connection wedged the whole listener until the process restarted, and — like the v0.9.4 `find_size` DoS — the **health watchdog does not catch it** (the runtime stays healthy; only the accept loop is stuck). Fixed with two separate bounds: a 10 s cap on the negotiation itself and a 750 ms cap on the post-session-end handoff wait (the window where the loop services nothing), guarded by a regression test that reproduces the hang. **The same PR fixes two more preemption bugs** found alongside it: the server-global eviction event could be drained by — and disconnect — the *winner* of a takeover (stale events are now discarded before serving a winner), and the anti-storm re-preempt lockout was uncapped, permanently barring the feature's own headline case (a dropped client reclaiming its own stale session) — now capped at 30 s. All found by the automated reviewer on upstream #1476 and confirmed present in the vendored copy.

## v0.9.4 — security hotfix: a pre-auth remote DoS in the RDP framing reader

A single-fix security release. **The default runtime path is otherwise unchanged** (no `src/` change — the fix is a vendored guard in the framing crate).

- **Fix (security): an unauthenticated remote client can no longer wedge the entire server with one malformed frame.** A 2-byte fast-path header (`04 00` / `00 00` — first byte `& 0b11 == 0`, length byte 0) made the vendored IronRDP framing reader (`ironrdp-async`'s `Framed::read_by_hint`) skip a **zero-length unmatched** PDU by reading `read_exact(0)` — no I/O, no forward progress, no `.await` yield — in an infinite loop, spinning a worker at 100% CPU **and wedging the acceptor's connection loop, so the whole server stops accepting = full outage**. It is reachable **before TLS/CredSSP**, so the connection-rate/lockout auth-guard never sees it, and the health-check watchdog misses it (the trivial runtime probe still runs on the other workers). macrdp now **vendors `ironrdp-async`** (a 4-file crate) at the current pin and guards `read_by_hint` to **fail on a zero-length unmatched PDU** — `Some((matched: false, length: 0))` → an `InvalidData` error → a clean per-connection rejection — instead of spinning. This is macrdp's own upstream PR **#1556** (commit `c541d09e`), complementing upstream **#1515**'s `find_size` hardening; either fix alone breaks the loop, and `ironrdp-async` is the lighter vendor. **Verified:** the exact 2-byte trigger fired ×10 at the fixed server left CPU at 0.0% (no spin, no pegged thread), the accept loop live (still accepting), and each connection cleanly rejected (the guard fires → `accept_begin failed` in the log). Found by the in-tree `soak_abuse3` decoder-fuzz harness (it had wedged a soak instance on the old build). The vendor dir drops when the IronRDP pin bumps past #1515 + #1556. See `vendor/ironrdp-async/CLAUDE.md`.

## v0.9.3 — storm-guard fix + the connection/input batch

A blank-recovery reliability fix plus four merged contributions (@antonmos). **The default runtime path is unchanged** except where noted; the headline is that the mstsc/Windows-App reconnect-blank loop can no longer run away.

- **Fix: the reconnect-blank drop loop now bounds instead of cycling forever (blank recovery).** The reconnect-storm guard (`MAX_CONSECUTIVE_DROPS`) is meant to stop an infinite drop → auto-reconnect → blank → drop loop, but its counter reset whenever a connection presented as few as `min_render_reports` (3) frames. A restart-while-connected reconnect-blank half-heals under the reactivation (a ~4-frame run) then relapses to black and is dropped — and that brief blip cleared the reset bar on **every** cycle, so the cap never tripped and the loop was infinite (live-repro'd on a Windows client over ZeroTier). The counter now resets only on an **established** connection (~5 s of *sustained* presentation — a genuine heal), so a brief-present-then-drop counts toward the cap, which trips after `MAX_CONSECUTIVE_DROPS` and ends the cycle (the session stays up with the "close+reopen your client" guidance). **Live-verified over ZeroTier:** the guard tripped at 3 drops with zero spurious resets, where the same path previously cycled indefinitely; the reset-on-brief-present logic is unit-tested (`storm_guard_should_reset`). Reverses a deliberately-documented-but-wrong earlier choice; removes the now-dead `ever_presented` method.
- **A second client now takes over the live session instead of hanging (#174, @antonmos).** `RdpServer::run` served one connection at a time, so a second client's connect sat unserved in the TCP backlog until the first ended — a silent hang. macrdp is single-console-session by design, so a newly-connecting client now **preempts** the live one — but only after it **fully authenticates** (real TLS, and CredSSP where the mode is Hybrid): an unauthenticated connection can never evict a live session (a cheaper "peek at the first bytes" gate was found to allow exactly that and was replaced). The candidate negotiates concurrently without touching the live connection's state (a cloned negotiation context + `Rc`-shared factories), and a just-evicted peer is briefly barred from bouncing back. Vendored `ironrdp-server` divergence (23); the mechanism is being discussed for upstream (Devolutions/IronRDP#1483).
- **Blank-recovery post-attempt heal-confirmation deadline (#175, @antonmos).** After a reactivation, the fallback drop could starve if the client emitted interleaved phantom nonzero-EDR reports (each resetting the consecutive-zero streak) or went QoE-silent. `QoeEvidence` now also tracks cumulative window tallies a phantom blip can't reset, and once a recovery attempt has run the session must show a sustained nonzero run within a deadline (`MACRDP_BLANK_RECOVERY_HEAL_CONFIRM_MS`, default 8 s) or the next attempt fires — gated on the client having acked frames since the attempt so an idle session is never mistaken for a starved blank. Complements the storm-guard fix above (the two gate opposite ends of the same loop).
- **`RelMove` + mouse edge-clamp (#176, @antonmos).** Relative mouse motion (trackpad-mode clients, e.g. the iOS Windows App) was silently dropped; it now applies the delta to the server cursor, clamped into the display. And `map_client_to_display` now clamps a mapped coordinate to the display's **last pixel** (`s-1`), not its size (`s`) — on a headless-vd layout `x==sw` was the *physical panel's first column*, so an overshooting client coordinate could walk the cursor off the vd onto the shielded panel (the "two live Docks" artifact). A correctness/confinement fix beyond the iOS hover-reveal case.
- **Clipboard pre-connect sync (#173, @antonmos).** Whatever was on the client's clipboard *before* connecting didn't reach the Mac pasteboard: the client's initial Format List triggered both a fetch of its clipboard and macrdp advertising the Mac's clipboard back, and under connect-time write contention the advertise could jump ahead of the client's own ack and corrupt its init handshake. macrdp now skips that one connect-time advertise (the pasteboard poller picks the Mac clipboard up shortly after).

## v0.9.2 — blank-recovery clean-presentation latch

A point release fixing a v0.9.1 regression in the mstsc/Windows-App reconnect-blank auto-recovery. **The default runtime path is unchanged**; only the blank detector's disarm logic changed.

- **Fix: a working session that presents fine but reports zero decode+render time is no longer force-dropped.** v0.9.1's #172 replaced the v0.9.0 one-way disarm latch (first nonzero EDR → detector off for the connection) with a *revocable* disarm, to catch a client that reported nonzero-EDR *while still black* after a reactivation. That regressed a client with the mirror behaviour — it **presents the desktop fine but reports `timeDiffEDR == 0` mid-session**, and its nonzero-EDR runs (3–14) never reach the "established" bar (40) — so the aggressive path force-dropped its working ~50 s sessions and the auto-reconnect cookie reconnected each time, producing a connect/disconnect loop on a session the user was actively using. Root cause: QoE decode+render-time is *bidirectionally* unreliable (one client class reports nonzero-while-black, another zero-while-presenting), so no EDR threshold separates them. The signal that does: **when** the nonzero run occurs. Fix (`src/h264.rs`): a durable **`presented_clean`** latch — a sustained nonzero-EDR run seen **before any recovery attempt has fired** (`attempts == 0`) proves the client painted the desktop at connect (it is not the reconnect-blank, which is black from frame one), so the detector latches off for the connection (the v0.9.0 behaviour, restored). The `attempts == 0` guard preserves #172: the blank client's nonzero-while-black flicker only appears *after* its reactivation, so the latch is withheld for it and the escalation still recovers it. **Live-verified:** a 6-minute session held (previously dropped every ~50 s) and a genuine reconnect-blank (`longest_render_run_before=0`) still self-healed. Trade-off: a genuine *mid-session* blackout on a cleanly-presented connection is no longer auto-recovered (an unconfirmed case) — `Ctrl+Alt+Shift+R` is the manual A/V-resync lever. Unit-tested (`blank_recovery_disarmed_by_clean_presentation`, `blank_recovery_clean_latch_does_not_shield_a_never_presented_blank`).
- **Known issue (deferred, not a regression): a blank-recovery *reactivation* un-blanks the `--capture-primary` physical panel.** With sessions no longer false-dropping, a genuine reconnect-blank heal (the bare core Deactivation–Reactivation) was observed to leave the physical primary showing the desktop — macOS resets the panels' gamma on the reconfiguration, and the recovery's same-size `Resize` skips the re-assert the live-resize path runs. Present since blank-recovery reactivation shipped (v0.8.27), only *noticed* now. A gamma-timing reblank fix was tried and was flaky, so it was reverted (kept on `wip/capture-primary-reblank-on-heal`); the robust fix is a shield-window helper (`--shield-primary` already avoids the whole class) and is deferred. See `docs/known-quirks.md`.

## v0.9.1 — the lockable-headless release

A new opt-in headless blanking mode that keeps the Mac lockable, a client-resolution feature for the virtual-display path, and a set of fixes. **The default runtime path is unchanged** (every functional change is opt-in, headless-only, or a client-specific corner case).

- **`--shield-primary` — an opt-in lockable headless blanking mode (#170; single-panel support #171, @antonmos).** A third headless mechanism alongside `--capture-primary`/`--detach-primary`, default OFF. Instead of gamma-blanking a captured panel (`--capture-primary`, which silently prevents the Mac from locking) or CGS-disabling it (`--detach-primary`, which macOS 26.x won't reliably re-enable — see #168 below), it covers each physical panel with an opaque black `NSPanel` drawn by a separate helper process (`gui/Sources/macrdpshield`, mirroring the `macrdphud` architecture — AppKit is main-thread-only and tokio owns main). Because no display is captured or disabled, **the Mac can still be locked**, and by default (`MACRDP_SHIELD_KEEP_PHYSICAL_MAIN=1`) the physical panel stays the system main so `loginwindow` draws the lock screen on it, visibly. It also has no ~250 ms resize flash (a window survives a display reconfiguration where a gamma LUT is reset by one). Config `PRIMARY_MODE=shield`. **Trade-off (kept, not hidden):** with the physical panel main, the remote desktop has no menu bar or Dock — they stay on the shielded panel — but it's usable via `Ctrl+Alt+G` to gather windows onto the visible display; and without capture the local pointer isn't confined (someone at the machine can move it, though clicks on the shield are swallowed). Engages on **single-panel auto-mirror hardware** (a MacBook with no external display) by breaking the vd→physical mirror + displacing the panel off the vd origin (#171), and **fails closed** — a failed engage re-mirrors and errors rather than leaving a visible desktop. New unauthenticated loopback IPC channel on `:40244` (same trust boundary as the other helper channels — do not expose off-loopback). Live-verified end-to-end on a second machine. Two adversarial reviews during development caught and fixed five real defects (an unacked IPC protocol that could report a shielded-but-visible desktop, a hotplugged-monitor gap, a bind-failure limp-on, a wedgeable accept loop, and blocking on the resize path).
- **Client-resolution auto-adopt on the `--virtual-display` path (#165, @antonmos).** The virtual display is now re-moded to the client's requested resolution at connect (and on live resize), so `--width`/`--height` are its *initial* size, not a pin — a phone and a laptop each get a crisp 1:1 desktop. `--no-client-resolution` restores the old fixed-size behavior. (Since the vd re-modes to match, captured == client, so there is no letterboxing on this path.)
- **Blank-recovery: sustained-EDR disarm + an established-session tier (#172, @antonmos).** The mstsc/Windows-App reconnect-blank detector's disarm was a one-way latch (`qoe_render_seen`) — the first nonzero decode+render report disarmed it forever, so a client that resumed reporting nonzero EDR *while still black* locked out the fallback drop that actually recovers it. It is now a pair of streaks: "presenting" requires the last N reports all nonzero (a brief blip no longer disarms) and any zero report re-arms it, and an **established** session (presented for ~5 s) tolerates that client's normal transient zero-EDR windows (with its own wall-clock bound) instead of being false-dropped. The connect-time reconnect-blank path is byte-for-byte unchanged; RTT scaling applies to the wall-clocks, not the presentation-quality bars. FreeRDP / QoE-less clients are untouched.
- **`Ctrl+Alt+G` gather now sweeps *mostly*-off-screen windows, not only fully-off ones.** The window-gather (headless modes) skipped any window overlapping the target display at all, so a window straddling the vd/physical boundary — mostly on the blanked panel, poking a sliver onto the vd — counted as "already visible" and was left half-cut. It now uses a majority-area test: a window is left alone only if ≥ half its area is already on the target. Fully-off windows still always move and fully-on ones still always stay.
- **`--detach-primary` restarts under launchd when macOS 26 can't re-enable the panel (#169, stopgap for #168).** On macOS 26.x the CGS app-scoped display *disable* is not reversible in-process (only the process exiting reverts it), so a `--detach-primary` disconnect could leave the built-in panel dark until the next manual restart. When headless (under launchd), macrdp now exits with a non-zero code (69) on that stuck-panel path so `KeepAlive` restarts a fresh process (~1 s, panel back). Inert on healthy hardware (the flag is only set when the re-enable actually fails) and for `--capture-primary`; off interactively. Config `DETACH_RESTART_ON_STUCK` / `MACRDP_DETACH_RESTART_ON_STUCK`. Live-verified on the 26.5.2 hardware that surfaced #168. This is a **stopgap, not a root fix** — issue #168 stays open.
- **iOS Windows App touch-mode taps land where you tap (#166, @antonmos).** A mouse PDU that carries a button flag also carries the pointer position, but the button event variants have no position field — so a client that sends a tap as a *single* button PDU with no preceding move (the iOS Windows App in touch mode) had its taps register at the previous cursor position. The button's position is now applied as a `Move` first. No-op for clients that already move-then-click (mstsc, the macOS Windows App). Vendored `ironrdp-server` divergence (21); a strong upstream candidate (bug filed as Devolutions/IronRDP#1466).
- **`--capture-primary` now warns, on every engage, that the Mac cannot be locked while it is engaged.** That mode blanks the physical panel by taking exclusive `CGDisplayCapture` of it, and `loginwindow` cannot draw its lock screen onto a captured display — so choosing Lock Screen (or ⌃⌘Q) silently no-ops and the machine stays unlocked behind the black panel (experimentally isolated across ~340 samples; `caffeinate` exonerated). The behaviour is unchanged — this is a **disclosure** fix, a `tracing::warn!` so an operator reading `macrdp.log` learns of it — plus the full write-up in `docs/known-quirks.md`. The real fix is `--shield-primary` above.
- **New doc: `docs/oss-rdp-server-comparison.md`** — the verified evidence behind macrdp's "first open-source RDP *server* to…" claims (presenting a client-redirected USB device, a working UDP multitransport data path, end-to-end client-webcam-as-native-camera — *that last one was refuted 2026-09-30, see below*), what **not** to claim, and an adversarial head-to-head against the closest peer (x6nux/macrdp). Read it before repeating any first-ness claim.

## v0.9.0 — the webcam release

*(First minor-version bump since the 0.8 series began — this one earns it.)*

**A webcam redirected from the client now presents as a real macOS camera.** Enable `--enable-camera-redirection` (config `ENABLE_CAMERA_REDIRECTION=1`), tick *Video capturing devices* in the client, and **"macrdp Camera"** appears in Photo Booth / Zoom / FaceTime / Teams showing the client's live webcam. As far as is known this makes macrdp the **first open-source RDP _server_ to present a client-redirected webcam as a native OS camera** *(**corrected 2026-09-30: it does not** — gnome-remote-desktop shipped the same end-to-end path on Linux in GNOME 50, 2026-02/03, before this release; what holds is "first on macOS", as far as is known. The pipeline, end to end: H.264 samples arrive over the MS-RDPECAM `RDCamera` DVC (plain TCP) → **VideoToolbox** decodes them to `420v` `CVPixelBuffer`s → macrdp (as a CoreMediaIO *client*) enqueues those onto the **sink stream of a CoreMediaIO Camera system extension**, IOSurface-backed so the handoff is **zero-copy** → the extension forwards them to its source stream, which is what apps see. Live-verified on real mstsc at 1080p/~30 fps with **zero dropped frames**.

- **Phase 1 — MS-RDPECAM negotiation.** The full server-side state machine (enumerate → open the client-named per-device channel → ActivateDevice → StreamList → media-type negotiation picking H.264 → StartStreams → the SampleRequest↔SampleResponse pull loop), in the vendored `ironrdp-server` (divergence 19) mirroring FreeRDP's `rdpecam` server. Samples flow over TCP, so UDP is **not** a prerequisite.
- **Phase 2 — decode.** `src/camera/decode.rs` reframes the Annex-B access units to AVCC and decodes via `VTDecompressionSession`.
- **Phase 3 — the macOS camera.** A hand-assembled (**no Xcode**) `.systemextension` built from a plain SwiftPM target, signed + notarized and activated from the menu-bar controller ("Enable macrdp Camera…"). Setup — the one-time Apple-portal artifacts, the build command, activation, and verification — is in **[docs/camera-extension-setup.md](camera-extension-setup.md)**.
- **Four silent CMIO failure modes** were found and are written up in that runbook, because every one of them fails with *no error at all*: the `.systemextension` filename must equal its bundle id; `CMIOExtensionClient.signingID` is literally the string `"unknown"` (so sink-producer authentication is impossible, and a rejecting hook surfaces to the producer as a bogus `-4`); **`kCMIOStreamPropertyDirection` is inverted** from its documented meaning, and starting the wrong stream *returns success* while nothing ever drains the queue; and macOS will not replace a same-`CFBundleVersion` system extension. ## v0.8.40 — the headless-laptop release

Three fixes for daily headless-laptop use (`--virtual-display` + `--capture-primary`/`--detach-primary`), plus a new which-client audit signal. **The default runtime path is unchanged; the first three are opt-in or headless-only.**

- **Windows follow you between local and remote (`--restore-windows-on-disconnect`, opt-in).** By default the virtual display is process-lifetime, so on disconnect its windows stay stranded on the (now off-screen) virtual display — invisible on a laptop's built-in panel until you reconnect. With this flag (config `RESTORE_WINDOWS_ON_DISCONNECT=1`), the last-client disconnect sweeps those windows back onto the built-in screen (Mac usable locally) and a reconnect auto-gathers them onto the virtual display the client sees (no `Ctrl+Alt+G` needed). Default off — a remote-only server still wants windows to stay on the vd so a reconnect lands with them in place. Reuses the `Ctrl+Alt+G` gather machinery; live-verified (6 windows swept home on disconnect). (#164)
- **The Dock no longer disappears on disconnect.** A follow-on to the v0.8.39 Dock fix: `CapturedPrimary::install` persists "the virtual display is the main display" into the WindowServer's session store (`ConfigureForSession`), but `drop` was reverting the arrangement only process-scoped (`ConfigureForAppOnly`) — so on disconnect the store still said the vd was main while the physical panel went back to `(0,0)`, and the Dock/menu bar *sometimes* followed the phantom vd off-screen. `drop` now persists the restore too (symmetric with install), so the store agrees the physical is main again. Crash-safety unchanged. Live-verified across repeated disconnects. (#164)
- **`--capture-primary` blanking survives a live resize.** A live re-mode (`applySettings` when the client maximizes / moves to a different-resolution monitor) is a display reconfiguration, and macOS resets the gamma tables on one — un-blanking the physical panel (which v0.8.39 keeps engaged across the resize, so nothing re-applied the gamma → the panel *stayed* on the desktop). macrdp now re-asserts the all-black gamma after the re-mode and after each post-resize window-gather sweep, so the panel reliably goes black again. **Known residual (documented):** a brief ~250 ms desktop flash *while the re-mode is in flight* — macOS shows the desktop during the reconfiguration and won't let a gamma write stick until it commits, so gamma blanking fundamentally can't cover that window (the only fix would be a black shield-window helper process, deemed not worth it for a local-panel flash during an intentional resize). (#164)
- **Client fingerprint in the audit log (`event="fingerprint"`).** A new per-connection audit record naming which RDP client connected — `client_name` (hostname) / `rdp_version` / `client_build` / `platform` — surfaced from the RDP handshake, in the human-readable log and (opt-in) the SIEM JSON stream. Fingerprinting, not authentication (a client can claim anything), but enough to tell clients apart at a glance: **mstsc** reports the machine's real Windows build + `WINDOWS/WINDOWS_NT`; **FreeRDP** hardcodes build 2600 + `UNIX`; **Thincast** = build 18363 + `UNSPECIFIED`. Live-verified on mstsc + Thincast. (#163)

## v0.8.39 — the smooth-resize release

Polish for live client-driven resize (the v0.8.37 feature) on the **headless** path (`--virtual-display` + `--capture-primary`/`--detach-primary`): resizing/maximizing the client window — including dragging between monitors of different resolutions — is now smooth and consistent. Scope is the headless resize path only; **the default runtime path is unchanged.**

- **No more session re-cycle on resize (flicker + sound cut).** A live resize needs a core deactivation–reactivation (the resolution genuinely changes), and the headless overlay watcher used to read the reactivation's brief session-count flap (1→0→1) as a real disconnect — dropping and re-engaging the headless capture (a visible gamma flicker) and restarting audio. The watcher now **polls for the session to come back** (up to a 2.5 s grace) instead of tearing down on the transient zero; only a count that *stays* zero is a real disconnect. The flap gap is variable (~0.5–0.9 s — it includes the virtual-display re-mode), which is why an earlier fixed-delay debounce wasn't enough. (#160)
- **The Dock and your windows now stay put across a resize.** Two stacked fixes: **(1) Root cause** — the headless mode places the virtual display at `(0,0)` to make it the system *main* display (that's what anchors the menu bar + Dock to it), but did so with a process-scoped, never-persisted setting (`ConfigureForAppOnly`), so **every re-mode re-derived the arrangement from the WindowServer's session store** — which still said "physical is main" — snapping the vd off `(0,0)`: the Dock jumped to the blanked physical panel and a variable-timing window relayout kept re-stranding app windows. Now the placement is **persisted for the session** (`ConfigureForSession`), so a re-mode has nothing to snap back to; crash-safety is unchanged (capture/gamma stay process-scoped, and a dead process's vanishing vd makes the physical main again automatically). **(2)** After each re-mode, macrdp re-asserts the vd as main (a now-no-op drift-catcher) and **auto-gathers** any window stranded off the re-moded display — the same sweep as `Ctrl+Alt+G`, run automatically because a resize is exactly when you expect your windows to follow. (#162, closes #161)
- Live-verified end-to-end on real mstsc over capture-primary: repeated maximize + drag-between-monitors with the Dock staying, windows staying, minimal sound interruption, and zero arrangement drift in the log.

## v0.8.38 — the A/V resync hotkey

A small feature release: an on-demand hotkey to recover a session that's gone stale after a long idle — a blanked screen and/or drifted audio — without disconnecting. **The default runtime path is unchanged.**

- **`Ctrl+Alt+Shift+R` — on-demand A/V resync.** An mstsc session left idle for hours can go stale on the client side: the picture blanks and the audio drifts (Windows' `audiodg` buffers playback downstream where the server can't observe it, so auto-detection is a dead end). This adds a manual lever you press when you *see* the drift — the **video** path forces a clean IDR keyframe to repaint the stale presentation, and the **audio** path rebuilds its capture stream so the client's drifted backlog drains and re-syncs (the same effect as a minimize→unminimize). No disconnect. Always-on like the existing `Ctrl+Alt+G` gather-windows hotkey, and Win-key-free so mstsc forwards it. Live-verified on real mstsc: un-blanked smoothly, audio resynced, zero flicker. The video deliberately uses an IDR rather than the heavier core reactivation — the reactivation un-blanks too, but on the `--virtual-display`/`--capture-primary` headless path it cascades into a visible ~1–2 s session re-cycle; the IDR is lighter and flicker-free.

## v0.8.37 — live resize + the webcam stall watchdog

Two additions on opt-in paths: the session can now **resize live when the client drags its window** (MS-RDPEDISP), and a **redirected USB webcam that freezes now recovers on its own** instead of staying stuck. **The default runtime path is unchanged.**

- **Live client-driven resize (MS-RDPEDISP), all session modes.** When the client resizes its window, macrdp re-negotiates the session at the new size on the fly — driving a core Deactivation–Reactivation (the same in-place machinery the mstsc blank-recovery uses) and, on a `--virtual-display`, re-moding the display like a monitor changing resolution. It's debounced, so a drag settles to a single reactivation. Verified live on **Windows App for macOS** (all session modes) and **FreeRDP**. On **mstsc it's a clean no-op** — DVC-level tracing confirmed mstsc doesn't emit the MS-RDPEDISP monitor-layout PDU on a window drag, so nothing changes there and there's no regression. Contributed by **Anton Mostovoy** (#155).
- **A frozen redirected USB webcam now self-recovers (stall watchdog).** A bulk webcam redirected over FreeRDP (`--enable-usb-redirection`, experimental / entitled build) could stream fine and then freeze after a while while the rest of the session kept working. The read-ahead engine delivers frame reads strictly in sequence order; a bulk read the client never completes — the camera stalls on the host (Linux USB autosuspend, a `uvcvideo` timeout, bandwidth) so its pending transfers hang — left a permanent gap with no timeout, so the stream wedged until the device was re-attached. A new `dispatch_source` watchdog detects a stream that's been waiting with no in-order data for `MACRDP_USB_STREAM_STALL_MS` (default 3000 ms; 0 disables), completes the waiting read with a zero-length transfer so macOS re-COMMITs the pipe, and re-engages read-ahead when the client resumes — turning a permanent freeze into a self-recovering hiccup (a permanently-dead camera becomes a bounded re-COMMIT retry loop instead of a silent freeze). Live-verified on FreeRDP + an A4Tech webcam: a client-side stall froze the picture, the watchdog fired at ~1.7–2.2 s, and the video resumed in Photo Booth with no disconnect or crash. The USB read-ahead knobs (`USB_STREAM_STALL_MS`, `USB_PREFETCH_DEPTH`) are now settable from `config.env`. The underlying trigger is client-side — the real fix for *why* a camera stalls is host-side (disable USB autosuspend) — this makes macrdp resilient to it. (#158)
- Docs: a new **Hotkeys** section in the README.

## v0.8.36 — the fork-workers removal

A cleanup release: it removes the experimental `--fork-workers` process model (superseded, and a net-negative for interactive mstsc) and lands opt-in, default-off groundwork for a future camera-redirection feature. **The default runtime path is unchanged** — single-process was already the default.

- **Removed the `--fork-workers` per-connection process model.** It ran a thin supervisor that `fork+exec`'d a fresh worker process per RDP connection (xrdp's model), built to dodge mstsc's H.264 EGFX reconnect-blank by giving each connection a fresh process. That blank has **self-healed in place since v0.8.27** — a bare core Deactivation–Reactivation (which preserves the EGFX channel/surface) plus the Server Auto-Reconnect Cookie — and an exhaustive live A/B found the process model was actually a *net-negative* for interactive mstsc: mstsc opens an abandoned extra TCP connection on each reconnect attempt, and because the supervisor serialized workers, that stalled the real connection's worker slot. Single-process + `--enable-h264` + blank-recovery + the auto-reconnect cookie is now the only, field-proven model. A stale `FORK_WORKERS=1` left in a deployed `config.env` is simply ignored (unknown key), so existing installs keep working; the GUI's "Per-connection workers" toggle is removed too. Net −756 lines (−691 in `main.rs`).
- **Experimental camera-redirection groundwork (Phase 0, opt-in, inert by default).** A new `--enable-camera-redirection` flag negotiates the MS-RDPECAM `RDCamera_Device_Enumerator` channel and logs the client announcing its redirected webcam — the protocol gate proving a modern mstsc/Win11 will hand macrdp a camera over MS-RDPECAM (the dedicated camera channel that generic USB redirection can't reach). It does **not** present a camera yet: no per-device stream, no macOS capture path. Nothing changes when the flag is off. This is groundwork for a future feature that presents a client's webcam as a native macOS camera.

## v0.8.35 — the USB read-ahead gate fix

A one-fix point release over v0.8.34. It reworks *how* the v0.8.34 gamepad fix distinguishes a streaming bulk endpoint from an HID interrupt endpoint, because v0.8.34's method silently broke the **webcam**. Scope is the opt-in USB feature only (`--enable-usb-redirection`, experimental / entitled-build-only); nothing else changes.

- **v0.8.34 fixed the gamepad but broke the bulk webcam.** v0.8.34 scoped the bulk-IN read-ahead engine (added in v0.8.30 for webcam streaming) to *true* BULK endpoints by pushing the client's `SelectConfiguration` `is_bulk` flag into the virtual host controller. That kept the gamepad's interrupt-IN pipe off the streaming path — but a **UVC video endpoint is frequently reported over the wire with `is_bulk=false`** (measured 69 of 81 times on a redirected A4Tech cam), so the declared-type gate *wrongly excluded the webcam*: read-ahead never engaged, so the video pipe ran dry and there was no image.
- **Fix: gate read-ahead on the transfer's read LENGTH, not its declared type.** Read length is a reliable physical signal where the declared transfer type is not — a webcam's streaming bulk read is tens of KB (102656 B observed), while an HID interrupt-IN poll is at most `wMaxPacketSize` (64 B). The read-ahead gate now engages only when the read is ≥ 512 B, so the webcam's large reads stream (byte-identical to the known-good v0.8.33 path) while the gamepad's tiny polls stay serial. Moving that size check up into the ring-walk gate — not just inside the engage step, where v0.8.30–0.8.33 had it — is what stops an interrupt endpoint's control flow from diverging into the streaming branch in the first place. The now-unneeded `is_bulk` plumbing is removed.
- Live-verified: the redirected Xbox controller's buttons work (1140 input reports, pipe stayed serial) and the webcam's read-ahead engages (`readLen=102656`, depth 4). Note that whether *mstsc* actually delivers a redirected webcam's frames is a client-side matter — mstsc prefers its dedicated camera-redirection channel and can refuse the raw-USB transfers (`0x8007001f`); the FreeRDP bulk-webcam path (the one originally verified in v0.8.30) is unchanged.

## v0.8.34 — the gamepad-input fix

A one-fix point release over v0.8.33. It repairs a real regression in **USB redirection** (`--enable-usb-redirection`, experimental / opt-in / entitled-build-only): a redirected **HID gamepad enumerated but its buttons did nothing** — broken since v0.8.30 and present in v0.8.31/32/33. Nothing outside the opt-in USB feature changes.

- **Redirected HID input works again.** A client-redirected Xbox controller would appear on the Mac (visible in `ioreg`, macOS binding its own gamepad driver, descriptors and `SelectConfiguration` and endpoint pipes all succeeding) while **no button or stick input registered** — and the device would periodically drop and re-enumerate. Its interrupt-IN input reports were arriving roughly **once every 20 seconds** instead of every ~8 ms.
- **Cause: the bulk-IN read-ahead engine (added in v0.8.30 for webcam streaming) was matching interrupt endpoints.** Its "is this a streaming bulk-IN pipe?" test was *address-only* — a non-EP0 IN endpoint carrying a normal transfer — which an **interrupt-IN pipe also satisfies** (an HID input-report endpoint is exactly that; only isochronous transfers carry a distinct message type). macOS double-buffers interrupt endpoints too, so its re-doorbell of the still-unadvanced transfer-ring head pushed the gamepad into the streaming branch instead of the plain "skip the duplicate, the outstanding transfer's completion will re-walk the ring" path. A large-read threshold stopped the read-ahead *stream* from actually engaging on a 64-byte report — which is why the bug hid for four releases — but the control flow had already diverged, so the pipe was only serviced when something else happened to force a ring re-walk.
- **Fix: gate read-ahead on the endpoint's real transfer type.** The server already learns each endpoint's true type authoritatively from the client's `SelectConfiguration` pipe info; it now hands that to the virtual host controller (before the kernel creates the endpoints, so it is always known before the first ring walk). An unrecognized endpoint defaults to *not* bulk, so the fail-safe is the serial path. Mass storage and the bulk UVC webcam keep read-ahead exactly as before; interrupt endpoints can no longer enter the streaming path at all.
- Live-verified on a real redirected Xbox controller (`045e:0b12`): steady input, no dropouts, no re-enumeration.

## v0.8.33 — the audit-forwarding release

A SIEM/SOC observability roll-up over v0.8.32. It turns macrdp's existing security audit events into a structured stream a log collector can forward, adds an explicit authentication-outcome event, and guards the whole path with an end-to-end CI test. **No change to the default runtime path — everything here is opt-in and default-off, and the default path is byte-identical when it's off.**

- **Opt-in structured JSON audit stream for SIEM/SOC forwarding.** macrdp already emits a per-connection security audit event (accept / reject / disconnect, with source IP+port, reason, and outcome) on a `macrdp::audit` tracing target. Point `--audit-file PATH` (or `MACRDP_AUDIT_JSON=1`, config `AUDIT_FILE`) at a file and those events are additionally written as **one JSON object per line** on a dedicated, self-rotating stream — a versioned (`schema_version`) contract a standard collector (Vector / Fluent Bit / rsyslog / Splunk UF) tails and forwards to a SIEM. macrdp deliberately does **not** speak network syslog itself: getting logs off-box reliably (TLS, buffering, backpressure) is the collector's job, and macOS has no first-class network-syslog daemon anyway. The human-readable `macrdp.log` audit lines are unchanged; the JSON file is an additional sink, emitted independent of `RUST_LOG` so a quiet operational filter never suppresses security events.
- **Explicit `event="auth"` login verdict.** A new audit event emitted the moment CredSSP/NLA resolves — `outcome="success"` when the client's credentials validate, or `"did_not_complete"` (with a short `reason`) when they don't — so a SOC sees the real authentication result instead of inferring it from the connection-duration heuristic. It fires once per connection, after the TLS upgrade (so a benign pre-TLS client blip can't produce a false failure). Single-process path; under `--fork-workers` the accept/disconnect audit is unchanged but no `auth` event is produced. Emitted for loopback too (audited, though guard-exempt).
- **Log-injection hardening of the audit `reason`.** The failure `reason` derives from an error produced while handling an *unauthenticated* client's exchange, and the human-readable logfmt sink writes fields verbatim — so an embedded newline could otherwise forge/split an audit line. The `reason` is now control-character-stripped (single-line printable token in both sinks) and length-bounded; it never contains credential material. The JSON sink was already escape-safe.
- **New documentation:** [`docs/audit-log.md`](audit-log.md) — a reader/analyst guide to every event and field with worked interpretation examples (normal session, wrong password, brute-force lockout, benign blip, loopback) — and [`docs/siem-forwarding.md`](siem-forwarding.md), with drop-in collector configs.
- **End-to-end CI coverage.** A new macOS CI job drives a real FreeRDP `+auth-only` CredSSP handshake (correct and wrong password) against a loopback server and asserts the JSON audit stream records the right accept/auth/disconnect events, outcomes, and correlation — a regression a `cargo test` can't catch (the test harness is TLS-only, no CredSSP). The reusable script is `scripts/test-audit-log.sh`.
- Also lands inert internal groundwork for isochronous USB endpoints (observe-only logging inside the experimental, opt-in, entitled-only USB-redirection feature) — no functional change.

## v0.8.32 — the security-hardening release

A security-focused roll-up over v0.8.31, plus two usability additions. No change to the default runtime path — the hardening is in the code that parses untrusted input and in the build/CI supply chain.

- **Fuzzed the network-facing decoders — found and fixed 3 real panics (#147, #149).** New `cargo-fuzz` harnesses over the two self-written protocol decoders a malicious client can reach: `ironrdp-rdpeudp` (the raw-UDP multitransport parser) came through ~250M executions clean, but `ironrdp-rdpeusb` (the URBDRC / USB-redirection PDU decoder) surfaced **three unchecked `read_slice` calls that panicked on a truncated PDU** (`TsUrbResult`, `IoControlCompletion`, `TsUsbdInterfaceInfoResult`) — an attacker-influenced panic on a decode path, now bounded with the same `ensure_size!` guard the sibling decoders use (107M executions clean after). Also fixes the frontmost-app detection the Cmd+`/Option+` window cycle uses under `--virtual-display`/`--capture-primary` — it now reads the system-wide AX focused application (real WindowServer focus, which reflects macrdp's own activations) instead of the `NSWorkspace` value that goes stale in headless modes. ## v0.8.31 — the gamepad-resilience release

A one-fix point release over v0.8.30 (the webcam release), hardening HID/gamepad USB redirection. A redirected USB device's **interrupt-IN endpoint** — e.g. an Xbox controller's input-report pipe — no longer goes dead when the client fails a single interrupt read. mstsc intermittently completes an interrupt read with `hresult 0x8007001f` (`ERROR_GEN_FAILURE`) while the device channel is still open; surfacing that as an endpoint STALL made the macOS class driver give up polling the pipe, so the gamepad "hung" after a few seconds. The server now treats a **channel-still-open transient failure on an interrupt endpoint as an empty poll** (0 bytes, success) so the OS keeps the pipe alive and re-polls — matching interrupt "no data ready" semantics (one dropped input report is imperceptible; the next poll gets fresh controller state). Scoped strictly to interrupt endpoints (`is_bulk == false`): mass-storage **bulk** pipes keep the strict stall so a real bulk error surfaces and a short read never corrupts a transfer, and link death (`channel closed`) stays fatal so teardown proceeds. Everything else in v0.8.30 is unchanged. (Field note: a physically **loose or jostled USB cable** produces the same dead-gamepad symptom — a genuine disconnect + re-enumeration — and is *not* software-fixable; reseat the cable. In the log a cable disconnect shows as `status=11` → `endpoint created ep=0x00` re-enumeration, which this fix correctly leaves alone.)

## v0.8.30 — the webcam release

A **bulk USB webcam redirected over FreeRDP now streams live video** into the Mac session (`--enable-usb-redirection`, entitled build) — as far as is known a first for any open-source RDP *server*. Verified live: an A4Tech FHD 1080P PC Camera (`09da:2692`, whose VideoStreaming endpoint is **bulk**, not isochronous) shows smooth moving video in Photo Booth on the Mac. The blocker turned out to be **USB read-depth starvation**, not the (separate, mstsc-only) camera-channel limitation: macOS double/triple-buffers a streaming bulk-IN endpoint — it queues several concurrent reads so the device's pipe never runs dry — but the user-space host controller's transfer ring exposes only **one** transfer at a time, so serving reads one-at-a-time *starved* the camera (it produced no data and macOS tore the stream down and retried in a loop), while the earlier behavior of re-forwarding the same read for depth dropped half the frame data (corrupt). macrdp now runs a **bulk-IN read-ahead engine**: it keeps several `bulk_transfer_in` reads in flight to the client at once (`MACRDP_USB_PREFETCH_DEPTH`, default 4), decoupled from the ring and buffered in **sequence order**, then hands one chunk to each ring transfer as it comes up — restoring the device's read depth with no data loss. It engages only for large streaming reads that show concurrent demand, so **mass storage** (regression-verified still byte-exact) and **interrupt/HID** endpoints (the redirected gamepad) are unaffected and stay on the serial path. Isochronous webcams remain unsupported (this camera is bulk); mstsc still can't stream a webcam over USB redirection (it routes camera video to a separate camera-redirection channel — a distinct future feature). No change to the default path — the whole feature stays inert unless the entitled build is used.

## v0.8.29 — the stability release

A bug-fix roll-up over v0.8.28 — four independent fixes, no new features.

- **Clipboard use-after-free crash fixed (#144).** A rare `SIGSEGV` during clipboard churn (in `-[NSPasteboard _updateTypeCacheIfNeeded]`) was root-caused to unsynchronized multi-threaded access of the process-global, non-thread-safe `NSPasteboard`: the change-count/advertise poller reading `pasteboardItems()`/`types()` could overlap a `clearContents`/`writeObjects` writer (paste / download / disconnect-teardown) and corrupt the type cache. Every pasteboard accessor now serializes behind a single process-global guard, with the check-then-clear paths holding it across the whole read-modify-write.
- **Scroll-wheel runaway on the macOS Windows App fixed (issue #113 / #140).** Scrolling *down* in the Windows App instantly jumped to the bottom of the page ("like pressing End"). Root cause: `ironrdp-pdu` decodes MS-RDPBCGR's 9-bit wheel-rotation field as sign-magnitude instead of two's complement (the `WHEEL_NEGATIVE` bit *is* the sign bit), so the client's gentle `-1..-3` trackpad deltas arrived as `-255..-253` — a max-speed scroll on every tick. mstsc masked it by scrolling in whole ±120 notches. Corrected at the vendored `ironrdp-server` handler (real fix filed upstream as Devolutions/IronRDP#1414/#1415), plus per-event delta accumulation so this client's fine-grained deltas aren't truncated to zero. Live-verified on the reporting client. (Contributed by Anton Mostovoy.)
- **Xbox controller Guide button no longer kills the USB-redirection session.** With `--enable-usb-redirection` and a redirected Xbox controller on mstsc, pressing the Guide/turn-on button disconnected the whole session: mstsc issues a `SET_FEATURE(DEVICE_REMOTE_WAKEUP)` control-OUT, which macrdp wrapped in a `TRANSFER_OUT_REQUEST` that the URBDRC codec rejects — and the encode error propagated out and tore the session down. Fixed by routing feature requests via `TRANSFER_IN` (matching real Windows) and making the URBDRC send path encode-tolerant, so no malformed URB can ever disconnect the session. HID/gamepad redirection is now verified on **both FreeRDP and mstsc** (a redirected Xbox controller is a live gamepad on the Mac).
- **`make-app.sh` dev signing now keeps TCC grants across rebuilds (#141).** Ad-hoc signing does *not* give a rebuild-stable identity (an ad-hoc signature has no certificate, so its designated requirement degrades to the binary's `cdhash`, which changes every rebuild and invalidates the Screen-Recording/Accessibility grants). `make-app.sh` now auto-prefers a local self-signed `macrdp-dev` code-signing identity when `CODESIGN_IDENTITY` is unset, making the requirement `identifier + certificate leaf` — stable across rebuilds. No change for explicit-identity (Developer ID / CI) builds. Docs corrected. (Contributed by Anton Mostovoy.)

## v0.8.28 — the gather-windows release

An on-demand hotkey — **`Ctrl+Alt+G`** (`Ctrl+Option+G` on macOS) — sweeps any window stranded **off** the virtual display back onto the display the RDP client sees. In the headless modes (`--capture-primary`/`--detach-primary`) the client sees the *virtual* display, which sits in a different region of the global coordinate space than the physical panel; a window opened on the physical panel before connecting — or one an app pops onto the primary mid-session — keeps its old coordinates and is invisible/unclickable over RDP. The hotkey walks each regular Dock app's windows via Accessibility (the grant macrdp already holds for input) and moves any window entirely off the target display to just inside its top-left; windows already (even partly) visible are left untouched. **Manual by design** — an on-connect auto-gather was built first and rejected as too surprising (it repositioned windows on every reconnect); the hotkey puts the user in control. The chord is deliberately Win-key-free so mstsc forwards it, and it's not a system shortcut on either OS. No-op when there's no virtual display. Live-verified on real mstsc over a `--capture-primary` session.

## v0.8.27 — the reconnect-blank-cracked release

The mstsc **reconnect-blank is fixed at last** — a client-side EGFX surface-retention bug that had been documented as "not server-fixable" for months (mstsc retains its output surface across an in-process reconnect and composites the stale one → black screen; the only recovery was to fully close and reopen the mstsc window). The breakthrough: on a detected blank, the server sends a bare RDP **core Deactivation–Reactivation** (Server Deactivate All → new Demand Active) that **preserves the EGFX channel and surface** — no surface delete, no channel close, no graphics reset (all of which were exhaustively proven client-fatal in prior attempts). Re-running just the core capability handshake makes mstsc **re-map its retained surface and present again, in place, with no disconnect**. **Live-verified on real mstsc/WiFi: 9/9 blanks healed across two runs, EDR=0 → presenting in ~1-2 s, zero drops.** It's the default recovery action now (a connection drop is only the fallback if the reactivation ever fails to heal). Detection was also sped up with a wall-clock fast-path so a static blank heals in **~4 s** instead of the previous ~70 s. Still RTT-gated and QoE-gated, so FreeRDP and high-latency links are untouched. **`--fork-workers` is no longer needed** for reconnect reliability (and stays a net-negative for interactive mstsc — see v0.8.26 notes); single-process + `--enable-h264` + blank-recovery is the recommended interactive config. Implementation is a zero-vendored-change injection (a no-op `DisplayUpdate::Resize` to the current size reuses the server's existing reactivation path).

## v0.8.26 — the roaming-client release

UDP multitransport now configures and cleans up after itself, so the UDP switches (`--enable-udp-multitransport`, `--enable-lossy-audio`) are **safe to leave permanently enabled on a client that moves between networks**. (1) **RTT-gated offer**: the server measures each connection's TCP round-trip time at accept and simply never offers UDP to links at/above ~80 ms — LAN/WiFi sessions get the loss-resilient UDP audio path, VPN/ZeroTier/mobile sessions run plain TCP from the first byte with no tunnel to wedge. (2) **Tunnel-lifecycle hardening**: an ended session's abandoned tunnel now retires quietly instead of triggering the 10-minute offer cooldown (a false cooldown that silently downgraded healthy-LAN reconnects); a tunnel that wedged *before* its session ended is still correctly adjudicated as dead so the reset-cycle protection can't be evaded; offer cookies are evicted on every connection end (previously leaked one registry entry per failed handshake, with a zombie-peer window); and all three peer-removal paths lower the shared tunnel flag so audio can never route into a nonexistent tunnel. (3) **`--fork-workers` parity**: workers sample the link RTT themselves, so the link-aware features (blank-recovery gate, bitrate seeding) apply under the per-connection-process model too. 

## v0.8.25 — the resilient-link release

three session-killers fixed, all live-verified over ZeroTier (including over a mobile connection). (1) **Oversized-cursor fix**: macOS "shake to locate" (or any enlarged pointer) at Retina backing pixels overflowed the RDP pointer PDU's 64 KB mask limit, and the encode error tore down the whole session — the sprite is now downscaled to fit, aspect- and hotspot-exact. (2) **Link-aware blank recovery**: the server samples the kernel's TCP RTT for every connection at accept; on fast links the mstsc reconnect-blank auto-heal works exactly as before, on slow links the evidence window scales with RTT, and past ~80 ms the force-drop is withheld — on high-latency links a *rendering* client reports zero render-time, so the old detector dropped working sessions every ~5 s and the repeated drops caused the very blank it exists to fix. (3) **RTT-seeded adaptive bitrate**: slow links start at ceiling/3 (6 → 2 Mbit) and climb as headroom allows, instead of overshooting a distant pipe for the first seconds. (4) **UDP tunnel-death detection**: a wedged multitransport tunnel now falls audio back to TCP within ~30 s and suppresses further UDP offers for a cooldown, so mstsc's ~60 s dead-tunnel reset reconnects as a stable plain-TCP session instead of cycling. 

## v0.8.24 — the remote-link release

(1) **RTT-aware rate control**: the `--adaptive-bitrate` controller now measures **standing queue delay** (each frame's ship→ack round trip minus the link's windowed-minimum RTT) instead of a frame count that conflated latency with congestion — a clean-but-distant link (VPN/ZeroTier at 200+ ms) keeps **full quality** instead of crater-climbing to 10 fps, a genuinely thin pipe degrades gracefully and converges to alive-and-in-sync (lab: standing queue drained 2.9 s → 45 ms on a saturated 500 Kbit link), and a **no-ack distress fallback** keeps the controller live even when a fully choked client stops acking entirely; IDR backoff now covers both transports. Verified on a real ZeroTier link. (2) **Windows App for Android support**: that client advertises EGFX with AVC disabled, and confirming-then-ignoring the pipeline was a protocol violation it hard-disconnected on ~2 s in — macrdp now declines the graphics pipeline at the channel level and serves legacy updates; verified on a real device. (3) **Blank recovery heals ~2× faster** (drop-first + a reconnect-storm guard; live-verified). (4) **A quieter server**: idle pollers park (0.0% CPU with no client), and per-mouse-move / per-frame WindowServer round-trips are throttled. Caveat shipped with it: `--enable-lossy-audio` is **LAN/WiFi-only** for now — over ZeroTier-class overlays its UDP tunnel can wedge and mstsc's ~60 s dead-tunnel timeout resets the session cyclically (fixed in v0.8.25 by tunnel-death detection; on main the offer is now also RTT-gated, so the switch is safe to leave on). 

## v0.8.23 — health-check watchdog

`launchd`'s `KeepAlive` only restarts macrdp on an outright *crash*; a process that's alive but **wedged** (a deadlocked async runtime, every worker thread blocked) would otherwise stay up and unreachable with nothing to revive it. The watchdog probes the runtime from a dedicated OS thread (which keeps ticking even when the runtime is stuck) and, on a sustained wedge, exits with a distinct code so `launchd` — or the `--fork-workers` supervisor — restarts a fresh process. Conservative by default (a wedge must persist ~90 s before a bounce, so load spikes never trip it), on when running headless under launchd, and env-tunable (`MACRDP_HEALTHCHECK*`); it closes the last reliability gap `KeepAlive` couldn't. 

## v0.8.22 — automatic mstsc reconnect-blank recovery

A reconnecting `mstsc` that lands on its own stale retained surface (decodes every frame but never composites — the long-standing "black screen on reconnect with `--enable-h264`") is now **auto-detected and healed with no user action**. Detection reads the client's own QoE Frame Acknowledge `TimeDiffEDR` (decode+render time): a blank session reports it as zero on every frame while a rendering one shows nonzero within ~200 ms — a signal proven by decrypted-pcap comparison and verified live. On detection the server drops the connection (straight away by default — the non-destructive fresh-surface remap was verified never to heal `mstsc` and is now opt-in via `MACRDP_BLANK_RECOVERY_MAX_ATTEMPTS`); a **Server Auto-Reconnect Cookie** (MS-RDPBCGR ARC) then makes `mstsc` reconnect *itself* and the fresh connection renders, with a consecutive-drop cap so a truly-stuck client gets clear guidance instead of a reconnect loop. Default on (`MACRDP_BLANK_RECOVERY=0` / `MACRDP_AUTO_RECONNECT=0` to disable); pairs with `--fork-workers`. 

## v0.8.15–v0.8.21 — the congestion-responsive rate-control arc

under packet loss an H.264 session now degrades gracefully instead of freezing. **`--adaptive-bitrate`** runs an AIMD controller (standing queue delay — ship→ack RTT minus the windowed-minimum link RTT, EWMA-smoothed — + hysteresis + a 3-zone hold) on **both** the UDP tunnel and the TCP path, so `--bitrate` is a ceiling that backs off under congestion; once it bottoms out, a **frame-rate floor** sheds fps (never to zero) so video stays choppy-but-steady-and-in-sync rather than freezing. An **EGFX-over-UDP watchdog** auto-de-migrates a wedged reliable UDP tunnel back to TCP (incl. proactively on minimize/restore). And **`--enable-lossy-audio`** streams RDPSND over a lossy UDP/DTLS tunnel with 1+1 redundancy (each datagram sent twice → p→p² loss) — soak-verified smooth on real mstsc at 5/10/15% loss where single-send glitches. All verified on real mstsc; every switch is opt-in, default (TCP) behavior unchanged. 

- **v0.8.21 — auth-guard false-lockout fix (#115).** Surfaced by the Tier 2.4 soak: the connection guard counted a legitimately *reconnecting* client (e.g. mstsc after a reconnect-blank or a flaky link) as a failed attempt and could lock it out. Only a connection that errors **and** fails within the fail-fast window (`MACRDP_GUARD_FAILFAST_SECS`, ~3 s — never authenticated, the brute-force signature) now counts toward a lockout; see the auth-hardening section of `docs/cli.md`.
