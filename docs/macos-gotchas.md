# macOS-specific gotchas

- **Screen Recording permission** (TCC) is required for ScreenCaptureKit. Granted in System Settings → Privacy & Security → Screen Recording.
- **Accessibility permission** is required to post synthetic keyboard/mouse events via `CGEventPost`. Granted in System Settings → Privacy & Security → Accessibility. Without it, posted events are silently dropped.
- **TCC grants are path-keyed AND signature-keyed — and ad-hoc signing does NOT give a rebuild-stable identity.** `target/debug/macrdp` and `target/release/macrdp` are tracked separately, and an unsigned rebuild at the same path invalidates the grant. **Correction (2026-07-05, contradicts an earlier version of this note):** ad-hoc signing (`codesign -s -`) does *not* make the grant survive rebuilds either — an ad-hoc signature has no certificate, so its designated requirement is `cdhash H"<binary hash>"` (check with `codesign -d -r-`), which TCC pins the grant to and which changes on every rebuild (confirmed live: three consecutive ad-hoc `make-app.sh` rebuilds each killed the Screen Recording + Accessibility grants). Ad-hoc still beats unsigned (stable within one build; content-addressed rather than per-link-random), but a **certificate identity is required for rebuild-surviving grants** — a free self-signed code-signing cert works (`macrdp-dev`; `packaging/make-app.sh` auto-prefers it, see packaging/README.md for one-time creation). With a cert the requirement becomes `identifier + certificate leaf`, stable across rebuilds.
- **Posting events to the login window or secure-input contexts** (password fields, lock screen) is blocked by the OS and cannot be worked around — document the limitation rather than fighting it.
- **Default RDP port 3389 is privileged**; bind 3389 only with elevated rights, otherwise default to 3390 in dev.
- **OpenPAM, not Linux-PAM.** `checkpw` uses `use_first_pass`, so `pam_opendirectory` reads the password from `pam_set_item(PAM_AUTHTOK, ...)` and never invokes the conv callback. See `src/auth.rs`.
- **`CGVirtualDisplay*` is a moving target.** macOS 26 (and presumably forward) replaced the older C-function surface (`CGVirtualDisplayCreate` / `ApplySettings` / `GetDisplayID`, which BetterDisplay's wrappers document) with an Obj-C class (`-[CGVirtualDisplay initWithDescriptor:]` / `applySettings:` / `displayID`). `private_api.rs` is written against the new shape only; if a future release renames a class or selector again, error messages from `VirtualDisplay::new` will name what's gone. BetterDisplay's open-source Swift wrappers are the canonical reference when adapting. Symbols are resolved via `AnyClass::get(...)` so missing-class failures are clean runtime errors, never link-time breakage.
- **Virtual-display refresh rate must be ≥ 24 Hz.** `applySettings` rejects modes below the real-monitor floor; the `VirtualDisplay::new` callers pass a hard-coded 60 Hz regardless of `--fps` (capture cadence is independent — `--fps` controls the SCK stream, refresh rate is metadata as far as the RDP server is concerned).
- **macOS 14+ killed every "activate this app" path except Accessibility for unsigned headless callers.** `NSRunningApplication.activateWithOptions` silently no-ops (front-app-only enforcement, `NSApplicationActivateIgnoringOtherApps` deprecated). `osascript tell application "X" to activate` requires TCC Automation, which an unsigned binary running without a UI session can't get prompted for. `/usr/bin/open -b <bundle>` doesn't activate AND re-launches just-quit apps. The one path that works: `AXUIElementSetAttributeValue(appRef, kAXFrontmostAttribute, true)` — macrdp already holds the Accessibility TCC grant (CGEventPost needs it), so no extra permission. Pair it with `AXRaise` on `kAXFocusedWindow` so the correct window of a multi-window process comes forward. For Electron apps (VSCode, Slack, Discord, Cursor) AXRaise on a window is often a no-op — layer `AXMain=true` on the target window + app's `AXMainWindow=<window>` to actually move the stacking. `NSWorkspace.frontmostApplication` is NOT trustworthy as live state after we've AX-activated something — it keeps returning the pre-activation frontmost; for "what app is the user in" use the internal `LAST_CYCLE_PID` cursor in `input.rs`.
- **A LaunchAgent's `ProgramArguments[0]` must be a code-signed Mach-O, never an unsigned shell wrapper — or Background Task Management re-prompts on every rebuild.** macOS Ventura+ surfaces every LaunchAgent in System Settings → General → Login Items & Extensions ("Allow in the Background") and posts a "Background Items Added" notification when it registers a *new or changed* item. BTM anchors a Developer-ID-signed launch target to a **stable identity (TeamID + signing identifier)** and approves it **once, surviving rebuilds**. An **unsigned script has no stable identity** (and a shell script can't carry an embedded signature — codesign only writes a fragile xattr that `cp`/notarization strip), so every bundle replacement + re-bootstrap looks like a brand-new unidentified item → re-notify, re-list, and it shows the script's ugly name instead of the app. `packaging/` originally launched an unsigned `macrdp-launch` wrapper (it translated `config.env` → flags) and hit exactly this. Fix (shipped v0.6.6): the `macrdp` binary reads `config.env` itself via `--config` (`src/main.rs::args_from_config`), so the LaunchAgent runs `Contents/MacOS/macrdp --config <file>` — the signed Mach-O directly. The wrapper was deleted. **Do NOT reintroduce a script (or any unsigned helper) as the launch target.** Migrating an existing install re-bootstraps the agent once (one last "Background Items Added"); from then on it's stable. Orphaned old "macrdp-launch" entries can linger in the Login Items list until BTM GCs them — harmless, toggle off if it bugs you.
- **QoS layering: tokio workers at USER_INITIATED, audio capture alone at USER_INTERACTIVE.** Under heavy local load (parallel cargo build, big disk I/O) the audio dispatch pipeline was preempted for hundreds of ms — sometimes seconds — producing audible drops and the vendor-server's "writer stalled" resyncs. Two-tier fix: `main.rs::boost_thread_qos` bumps every tokio worker to `QOS_CLASS_USER_INITIATED` (0x19) via `on_thread_start` (the *main* thread is intentionally NOT boosted — doing so broke ScreenCaptureKit's display enumeration on mstsc connect, reproducibly), and `audio.rs::MacRdpsndBackend::start` spawns a dedicated std::thread per connection at `QOS_CLASS_USER_INTERACTIVE` (0x21) hosting a `current_thread` tokio runtime for the SCK pump + rubato resample + channel send. **Do NOT also boost the `egfx-ship` thread (h264.rs) to USER_INTERACTIVE — it was tried and made stutter worse.** Apple's scheduler treats USER_INTERACTIVE as scarce; a second long-running thread there starves the USER_INITIATED tokio worker doing the actual wire writes, so encoded frames pile up faster than they ship. Audio alone fits; audio + ship doesn't. Ship thread is fine at the USER_INITIATED it inherits from its tokio-worker spawn site. **Residual limit (reported 2026-06-18): a full-core local workload on the same Mac (e.g. `cargo build`, big disk I/O) still preempts the video encode/ship + audio dispatch (all on USER_INITIATED workers) and makes A/V choppy** — distinct from the RDPDR socket-writer contention, though it surfaces via the same audio-drop mechanism, and the server-side QoS levers are already maxed (boosting ship higher backfires, above). The effective fix is **workload-side: run the heavy job at background QoS so the scheduler favors macrdp's boosted threads** — `taskpolicy -b <cmd>` (e.g. `taskpolicy -b cargo build`), or throttle with `-j N` / `nice`. A software RDP server inherently shares the CPU; nothing server-side fully eliminates contention when every core is pinned at equal priority.
- **The account password lives in the Keychain, and BOTH ends deliberately go through the `/usr/bin/security` CLI — do not "harden" one side to the Security framework in isolation.** The GUI controller writes it with `security add-generic-password -U -s macrdp -a <user> -w <pw>` (`gui/Sources/macrdptray/main.swift::promptAndStorePassword`) and the server reads it with `security find-generic-password -s macrdp -a <user> -w` (`src/main.rs::read_password_from_keychain`, the `--keychain` / default `USE_KEYCHAIN=1` path). It's encrypted at rest — never plaintext on disk, and there's no `PASSWORD=` key in `config.env`. Using the **same `security` tool on both ends is load-bearing**: the entry's trusted-app context becomes `/usr/bin/security`, so the **launchd-started (headless) server reads it with no Keychain prompt**. A headless server *cannot answer* an auth prompt, so anything that re-points the entry's ACL away from `/usr/bin/security` breaks startup auth (silent failure or an unanswerable prompt). The in-memory copy is a `Zeroizing<String>` (wiped on drop), except the clone ironrdp keeps live for NLA/CredSSP. The `--password` CLI flag is the one plaintext exposure (visible in `ps` / shell history) — kept for compatibility but it warns at startup (`main.rs`); prefer `--keychain` or the interactive prompt.
  - **Possible future hardening (NOT low-risk — deliberately deferred):** the controller passes the password as a `security … -w <pw>` argv, so it's briefly visible in `ps` for the duration of that one subprocess while *storing* (a sub-second, local-only window). The "clean" fix — write via `SecItemAdd`/`SecItemUpdate` with a `SecAccessControl` ACL and read via `SecItemCopyMatching` — must change **both** the controller (write) **and** the server (`read_password_from_keychain`, read) in lockstep, with the code-signed trusted-app list set so the **headless launchd server still reads without a prompt**. Headless Keychain access is finicky and the failure mode is bad (server hangs / auth-fails on an invisible prompt). Since the fix only closes a momentary local `ps` window, the cost/risk outweighs it; left as documented future work — to be done as a separately-tested effort with real-client verification of the LaunchAgent path, never as a quick one-sided change.
- **A sleeping Mac stops accepting RDP connections, and macrdp can't fully prevent sleep — `caffeinate` is not enough on battery or with the lid closed.** Reported as a "regression" 2026-06-30: after a few minutes idle the client couldn't connect "until I press the laptop's keys." It is **not** a macrdp bug — when reachable the listener answers (verified live), and the `pmset -g log` showed the Mac entering `Idle Sleep` / `Maintenance Sleep` / `Clamshell Sleep` and only waking on local input. Once macOS sleeps, an ordinary RDP TCP SYN does **not** wake it (`womp`/Wake-on-LAN fires only for a magic packet, which mstsc/FreeRDP don't send); only local HID input or opening the lid does a FullWake, after which macrdp (which never died) answers again. macrdp already runs `caffeinate -dimsu -w <pid>` for its whole lifetime (`src/main.rs::prevent_sleep`, default on; `--allow-sleep` opts out) and that holds `PreventUserIdleSystemSleep` + display + disk assertions — but it **cannot** cover two cases, by Apple's design, from an unprivileged user-space process:
  - **On battery:** `caffeinate -s` (PreventSystemSleep) is **AC-only** and ineffective on battery; the machine still drops into Deep Idle / "Maintenance Sleep" (the battery power profile is typically `sleep 1` = idle-sleep after 1 min). The `-i` idle assertion does not stop the battery Deep-Idle/standby path.
  - **Lid closed (clamshell) on AC with no external display:** macOS forces `Clamshell Sleep` regardless of any assertion — a MacBook stays awake lid-closed only with an external display (and keyboard/mouse) attached.
  No user-space lever (caffeinate or an `IOPMAssertion`) overrides either; doing so needs root. So macrdp does **not** attempt it. **Operator fixes for an always-reachable server:** run it on **AC with the lid open** (the AC profile is usually `sleep 0`, no idle sleep), or attach an **external display** for lid-closed use, or disable sleep system-wide with **`sudo pmset -a disablesleep 1`** (covers clamshell + battery; revert with `disablesleep 0`; drains battery). This is documented, not fixed — a software RDP server on a laptop inherits the laptop's power policy.
- **The feature-gated helper channels are UNAUTHENTICATED loopback IPC — the security model assumes a trusted local user.** Several optional features open a plain `127.0.0.1` TCP listener with no handshake or shared secret, so **any local process running as the user** can connect to them while the feature is active. None is remotely reachable (loopback-only) and all are off by default, but the trust boundary is deliberate and worth stating: macrdp's local security model is that of a normal single-user desktop — a hostile *local* process is out of scope, the same assumption `ssh-agent`/`pcscd`/most desktop IPC make. The channels: (0) **stats endpoint** (`:40245`, `--stats-endpoint`, `MACRDP_STATS_PORT`) — the least sensitive: a **read-only** listener that writes one JSON line (current H.264 bitrate / RTT / fps / frame count / session dimensions — no client IP or hostname) and closes; it never reads request bytes, so it has no server-side input-parse surface. A local process could read the local session's own A/V perf numbers (low value) or **squat the port before macrdp binds** and feed the menu-bar controller fake stats (cosmetic — a wrong number in the Status pane). Handled inline with a 2 s write-timeout so it can't be wedged, and off by default. (1) **smart-card bridge** (`:40242`, `--enable-smartcard-redirection`, `MACRDP_SCARD_PORT`) — the sharpest one: a local process could speak the IFD protocol and drive the client's redirected smart card as an APDU oracle (bounded by the card's own PIN gate for protected operations, and only while a card is redirected). The command-APDU length is capped (`MAX_APDU_LEN` in `src/rdpdr/smartcard.rs`) so a bogus wire length can't force a huge allocation; a shared-secret handshake was considered and deliberately deferred (loopback + feature-gated + single-user ⇒ low severity, and wiring a secret into the `slotd`-loaded IFD handler cleanly is non-trivial — the same "don't change one end of a two-party contract in isolation" caution as the Keychain path). (2) **NFS mount** for drive redirection (`127.0.0.1:<ephemeral>`, `--enable-drive-redirection`, `nolocks`) — a local process could read/write the client's redirected drive while it's mounted (it's already the user's own drive, visible in Finder). (3) **app-switcher HUD** (`:40243`, `--app-switcher-hud`, `MACRDP_HUD_PORT`) — a local process could push a spoofed switcher overlay (cosmetic; appears only in the captured stream). (4) **shield-window helper** (`:40244`, `--shield-primary`, `MACRDP_SHIELD_PORT`) — **the sharpest of the loopback channels after the smart-card bridge, and the one whose consequence is least like the others'**: it controls a *privacy* mechanism, not a cosmetic one, so a single byte (`printf '\x03' | nc 127.0.0.1 40244`) tears down every shield and exposes the live remote session on the physical panel. macrdp is not notified and does not re-assert except on a virtual-display re-mode. A local process can also **squat the port before the helper binds** — the helper now exits rather than limping on with no listener, but a squatter that speaks the three-byte ack could still report a shielded desktop that is fully visible. A shared secret was considered and **deliberately not added**: macrdp would have to pass it to the helper via the environment, which any same-user process can read (`ps -E`), so it would raise the bar only against accidents — and a hostile same-user process is explicitly outside this model, exactly as for the three channels above. The honest summary is that `--shield-primary`'s blanking is robust against *mistakes*, not against a *local adversary*; if your threat model includes one, that is another reason a locked Mac (which this mode is meant to make possible again) is the real control. Do **not** expose any of these ports off-loopback.
